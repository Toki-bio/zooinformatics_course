Searching Sequences

New here? Start with the basics of this lesson: a few short blocks with things to try.

Almost every step of the earlier lessons was a search: a primer in an amplicon, the copies of a SINE in a genome, the place a read came from, the reads of another species in a library. The question looks the same each time, but the right tool depends on three things: whether the match must be exact or may differ, how many queries there are, and whether the same target will be searched again. This lesson builds the tools in that order. It ends with k-mer sketches for comparing whole data sets, and a helper for picking the smallest tool that answers the question.

Every section has a toy to try, and the figures are drawn from simple models so that you learn to read real output, not to replace it. Commands and defaults were read from each tool's own manual and source code at the versions named in each section. The worked example in section 05 uses a public Illumina library and names the lab tool, which is not yet public; other examples come from the lab's desman and SINE work. 01The search problem

Almost every step in the earlier lessons was a search. Where is this primer? Where are the copies of this SINE? Which place in the genome did this read come from? Is any of this library from another species? The question looks the same each time, but the right tool changes with three things: how exact the match must be, how many questions you ask, and how often you will search the same data. This lesson builds the tools in order, from grep to read mappers. This section sets out the problem and gives you a toy calculator for the biggest choice: scan the data every time, or build an index once.

The words

Query
The sequence you are looking for: a primer, a SINE consensus, one read.
Target
The sequence you look in: a genome, a set of contigs, a whole sequencing library. Some tools call it the database, bank or subject.
Hit
A place where the query matches the target well enough to be reported. "Well enough" is a rule you set, and the rest of the lesson is about how different tools set it.
Exact match
Every letter of the query is identical to the target, in the same order.
Approximate match
The query matches after allowing some differences: mismatches (one letter replaced) and gaps (letters inserted or missing).

One query or millions, scan or index

The second axis is how many queries you have. One primer against one amplicon is a task for the search box of a text editor. A sequencing library is millions of reads, each a separate query against the same genome. A method that takes a minute for one query is no problem once and a disaster a million times.

The third axis is how often the target is reused. If you search one genome with many queries, work you do once on the target can be shared. This is the choice between two designs:

Scan
Read the whole target from start to end for every query (or for every batch of queries). Nothing to prepare; the cost of each query is proportional to the size of the data.
Index
Read the target once and build a lookup structure, like the index at the back of a book. Each later query goes straight to the right place. You pay the build time up front, and you must store the index, which can be larger than the sequence itself.

Simple explanation with examples: a library and its index

You want to know where, in a large library, the books mention a rare plant. Without an index you open every book and read every page; you can start at once, but you will do it all again for the next plant. With an index you first spend a long time compiling a list of every word and its pages. Then each plant takes seconds.

If you have one plant to look up, compiling the index is a waste: you read the books once either way, and reading is cheaper than reading plus compiling. If you have a million plants, reading the library a million times is hopeless, and the index wins within the first few questions. The calculator puts numbers on this. The turning point is about build cost ÷ (1 − lookup cost) queries, with both costs measured in scans, so it depends mostly on how expensive the build is compared with one scan.

Two things the toy leaves out. First, an index only helps if the question can be answered from the list: an index of exact words does not find a word spelled with a typo, unless the tool also tries the typos. Second, the index takes space, and on a laptop it may not fit. Both come back in sections 08 and 09 of this lesson.

What "sensitive" and "fast" cost

A search can fail in two ways. It can miss a real hit, which is low sensitivity. Or it can report a place where the match is only by chance, which is low specificity. Making a tool more sensitive means letting weaker matches through. That lets in more chance matches, and it is slower, because weak matches are more numerous and each must be checked.

Speed usually comes from not looking at most of the data. A fast tool decides that most places in the target cannot contain the query, using a cheap test, and only examines the places that pass. If the cheap test wrongly rejects a real hit, the hit is lost, and the tool does not tell you. That is the price of speed. The rest of the lesson shows the cheap tests one by one: exact words (03, 04), short seeds that must match exactly before the match is extended (07), and indexes of the target (08). Section 06 first shows the slow, exhaustive reference: comparing the query with every place in the target by dynamic programming.

In our projects. The lab's own tools sit at different points on this scale. Our public SINE-copy scanner sear2k (lesson 7, section 02) accepts the cost of an exhaustive alignment so as not to lose diverged copies. At the other end, a lab tool that is not yet public looks for exact short words (k-mers, lesson 1) from a list of target sequences directly in sequencing files, and is a custom program because for that job reading the data was the cost that mattered. Simple explanation with examples: four questions before you choose a tool

Ask these four questions, in this order. (1) Must the match be exact, or may it differ? (2) How many queries? (3) Will I search this same target again? (4) What do I lose if the search misses a hit, and what do I lose if it reports a false one?

Examples. "Does my amplicon contain this primer": exact, one query, no reuse: a text search. "Which reads in this library contain this adapter": exact, one query, millions of reads: a scan with a fast tool. "Where in the genome does each of these ten million reads belong": approximate, millions of queries, the same genome: an index. "Where are the old copies of this SINE": approximate, few queries, one genome: a sensitive search, even if slow. Section 11 turns these questions into a helper.

02Line tools: grep to agrep

The oldest way to search a sequence file is the same tool you use on any text: grep. It is fast, it is already installed, and for a short exact motif it is often all you need. But grep was built for text, and a sequence file is not text in the way it expects. This section shows the tools in the grep family, what each one adds, and the five ways they quietly give a wrong answer on FASTA.

Trap 1: wrapped lines

FASTA files are usually wrapped at 60 or 80 letters per line, so a motif that crosses a line end is split in two and no line contains all of it. A toy file, with the pattern GGCTTAACCGATTAC crossing the end of the first line of seq1 (the file is shown first):

>seq1 toy
ACGTTGCAAGGCTTAAC
CGATTACAGGGATCCTA
GGCATTTACGCGAATTC
>seq2 toy
TTGAGCTCCCTGTAATC
GAGTTCCTAGCATGCAA
$ grep -c GGCTTAACCGATTAC toy.fa
0
$ awk '/^>/{if(s)print s;print;s="";next}{s=s $0}END{print s}' toy.fa > flat.fa
$ grep -c GGCTTAACCGATTAC flat.fa
1

The awk line joins the sequence lines of each record into one line. It is the cheap fix. Join per record, as the awk does: removing every newline from the whole file would glue the end of one record to the start of the next and could create matches that exist in no sequence. seqkit grep -s avoids the problem because it reads records, not lines.

Trap 2: the other strand

DNA is double-stranded and a copy of a motif can sit on either strand. grep looks for the text you typed. The reverse complement is the pattern read backwards with A and T swapped and C and G swapped; here it is GTAATCGGTTAAGCC, and you have to search for it separately:

$ echo GGCTTAACCGATTAC | awk '{o="";for(i=length;i>0;i--)o=o substr($0,i,1);print o}' | tr ACGT TGCA
GTAATCGGTTAAGCC
$ grep -c GTAATCGGTTAAGCC flat.fa     # the toy file has no copy on this strand
0

seqkit grep -s -p PATTERN does this for you: its help says that when searching by sequence "both positive and negative strands are searched" and that -P restricts it to the positive strand. This was read from the seqkit 2.14.0 help and source. seqkit is not installed on the machine where we ran the other commands, so its commands on this page were not run.

Trap 3: compressed files

Sequencing data usually comes as .fastq.gz. The letters in a gzip file are not the letters of the sequence, so grep on it finds nothing. Decompress into a pipe:

$ grep -c TAAC toy.fa.gz
0
$ gzip -dc toy.fa.gz | grep -c TAAC
1
$ rg -c TAAC toy.fa.gz       # no -z: nothing is printed, exit status 1
$ rg -z -c TAAC toy.fa.gz
1

A zero without an error message is the dangerous part: it looks like "the motif is not in the data".

Trap 4: one pattern or many

-f FILE reads one pattern per line and prints lines that match any of them. Add -F when the patterns are plain letters, so they are not read as regular expressions:

$ printf 'TAAC\nGGGATCC\n' > pats.txt
$ grep -F -f pats.txt toy.fa
ACGTTGCAAGGCTTAAC
CGATTACAGGGATCCTA
$ printf 'TAAC\n\n' > p2.txt      # a blank line sneaked in
$ grep -c -F -f p2.txt toy.fa
7

The last result is every line of the file (7), because a blank line is an empty pattern and the empty pattern matches everywhere. The GNU manual says "the empty regular expression matches the empty string"; a stray blank line in a pattern file is a common cause of "everything matched". The output also does not say which pattern matched a line.

Trap 5: counting versus extracting, and the locale

-c counts lines, not matches; ripgrep's guide says the same ("a count of total matched lines"). -o prints each match on its own line, so counting those counts matches:

$ printf 'AAAAAA\n' | grep -c AA
1
$ printf 'AAAAAA\n' | grep -o AA | wc -l
3

-o finds matches that do not overlap, so AAAAAA holds 3 hits of AA, not 5.

The locale is the setting that tells programs which alphabet and sort order to use (LANG, LC_ALL). The GNU manual says it changes how character classes and bracket expressions are read, and that the traditional reading is obtained with LC_ALL=C. You will often read that LC_ALL=C grep is also much faster; the manual does not say this. We timed one pattern in a 122 MB text file of 2 million random 60-letter lines with LC_ALL set to C, en_US.UTF-8 and C.UTF-8: all three took about 0.44 s. That machine has no en_US locale installed, so the test tells us nothing about a typical Linux server. The speed gain from LC_ALL=C is not verified here. One more locale effect we did see: grep -P refused to run under LC_ALL=C on that machine ("supports only unibyte and UTF-8 locales"), so we ran it with C.utf8.

Regular expressions and multi-line search

With -E or -P you can write GG[CT]TT for "GG, C or T, then TT", or A{2}C. Neither is an alignment: the pattern stays exact except where you spell out the choices. Ripgrep can match across line ends if you ask: -U ("permit matches to span multiple lines") lets you write the line break into the pattern:

$ rg -U 'GGCTTAAC\nCGATTAC' toy.fa
ACGTTGCAAGGCTTAAC
CGATTACAGGGATCCTA
$ rg -c -U 'GGCTTAAC\nCGATTAC' toy.fa
1

This only works if you know where the line break falls, which depends on the wrapping width of the file, so it is not a general fix for Trap 1.

Allowing errors: agrep and seqkit

Real copies differ from the pattern. agrep from the TRE library "prints lines approximately matching a pattern". Its manual gives the example agrep -2 optimize foo.txt, which "outputs all lines in file foo.txt that match 'optimize' within two errors". Options -D, -I and -S set the cost of a deletion, an insertion and a substitution, and -B prints only the best-matching records. Like grep it works on records, which by default are lines (-d changes the record delimiter), so the wrapped-line trap applies in full. agrep was not run: it is not installed here, and we read its manual page only.

seqkit grep -s -p PATTERN -m 2 allows up to 2 mismatches. Its help says "Only substitutions are allowed; insertions and deletions are not", and that a single pattern of up to 64 characters with 1 to 4 mismatches uses an optimized search. The help also warns that for large genomes "using mapping/alignment tools would be faster". That points ahead: the later sections of this lesson are about those tools.

These tools scan every letter of the file again for each search. For one short motif in a few files that is fine. For millions of patterns, a pattern with gaps, or a genome you will search many times, continue with sections 03 and 08.

Simple explanation with examples: why "grep says zero" is not the same as "it is not there"

Think of a file as a long strip of paper cut into rows of equal length and stacked. grep reads one row at a time. If your word starts at the end of one row and finishes on the next, no single row contains it. Joining the rows into one strip fixes that. Searching only for the word as written misses the copy printed on the back of the strip, which is the other strand. And a compressed file is the strip put through a shredder: the letters you search for are not in it until you unpack it.

So after a zero from a line tool, ask three questions: is the file wrapped, did I search both strands, and was the file compressed?

03How exact search works

Section 02 used grep and agrep as black boxes. This section opens them. There are five ideas: the naive scan, Boyer-Moore skipping, Knuth-Morris-Pratt, Aho-Corasick for many patterns, and bitap for errors. Each one saves a different kind of work. At the end we say which of them the two programs really use, as read in their source code.

The naive scan

Put the pattern under the start of the text. Compare letter by letter from the left. At the first difference, move the pattern one position to the right and start again. An alignment here means one such placement of the pattern against the text, with no gaps.

This is correct, and on random DNA it is not terrible, because most alignments fail at the first or second letter. The trouble is repeats. Search for AAAAAB in a long run of A and every alignment costs the full pattern length. Boyer and Moore, citing Knuth, Morris and Pratt, put the worst case at a number of comparisons "on the order of i * patlen": the position reached times the pattern length. Genomes are full of such runs (lesson 3, s02).

Knuth-Morris-Pratt: never go back in the text

The naive scan forgets. Suppose the pattern is ATATC and the text reads ATATA…. The first four letters matched and the fifth failed. You already know the last two letters read were AT, and that is how the pattern begins. So slide the pattern and go on from the letter where you stopped, without reading anything twice. How far to slide depends only on the pattern, so it can be worked out once, before the search. In Boyer and Moore's summary, this algorithm "inspects each of the first i + patlen - 1 characters of string precisely once".

That guarantee removes the worst case, but every letter is still read. Remember the idea of a prepared table of "where to fall back to". It comes back in Aho-Corasick.

Boyer-Moore: compare from the right, then jump

Boyer and Moore (1977) changed one thing: compare from the last letter of the pattern. If the text letter there does not occur in the pattern at all, no alignment that covers this letter can work, so the pattern jumps its whole length past it. The letters jumped over are never looked at. Two prepared tables decide the jump, and the larger one wins:

Bad-letter rule
Look at the text letter that caused the mismatch. Slide until the nearest copy of that letter in the pattern lies under it. If the pattern does not contain the letter, slide past it. The paper calls this table delta1.
Good-suffix rule
The tail of the pattern has already matched. Slide until that same tail can line up again, preceded by a different letter. The paper calls this table delta2.

The paper's own figure: "For a random English pattern of length 5, the algorithm will typically inspect i/4 characters of string before finding a match at i". The longer the pattern, the longer the jumps. The authors call this "usually sublinear": it reads fewer letters than the text contains. The file must still be read in from disk, so the saving is in the work done per letter, not in the reading (s05 shows when reading becomes the limit).

Simple explanation with examples: why starting from the right lets you skip

You look for the word TIGER in a long line of print, and you hold a card with a five-letter window. Look only at the last letter in the window. It is Q. There is no Q in TIGER, so none of the next five placements of the word can cover this Q. Move the card five letters at once. You have checked one letter and passed five.

If the letter is G, it is in the word, third from the left. Move the card two letters, so that the G of TIGER lies on it, and look again.

Starting from the left gives you much less. A first letter that differs only tells you this one placement failed, so you may move by one.

Aho-Corasick: many patterns in one pass

Now you have fifty primers, or a thousand adapters. Running one search per pattern reads the text fifty times. Aho and Corasick (1975) build one machine from all the patterns and pass the text through it once. They say their approach "combines the ideas in the Knuth-Morris-Pratt algorithm" with those of finite state machines. Three parts make up the machine:

Goto (the trie)
All patterns are stored in one tree of letters, a trie. Patterns that start the same share a path. Each node is a state, and a state means "the last letters read spell this path".
Failure links
When the next letter has no edge, the machine does not start over. It follows a link to the state for the longest ending of what it has read that is also the start of some pattern. This is the Knuth-Morris-Pratt fall-back, for many patterns at once.
Output
Each state lists the patterns that end there, including shorter ones hidden inside. In the DNA example, state 8 reports ATCG and also TCG.

The paper states the two costs. Building the machine "takes time proportional to the sum of the lengths of the keywords". And "the number of state transitions made by the pattern matching machine in processing the text string is independent of the number of keywords". So a thousand patterns cost about the same text pass as one, but each letter is read: Aho-Corasick does not skip.

Bitap: all partial matches at once, and errors for little extra

All the methods so far need exact equality. Wu and Manber (1991) needed something else: a match within k errors, where an error is one substitution, insertion or deletion. That count is the edit distance. Their method builds on the shift-or idea of Baeza-Yates and Gonnet. The routine in agrep is called bitap, and we use that name.

Keep one bit per pattern position. Bit i says "the first i letters of the pattern match the text ending just here". Prepare one mask per letter of the alphabet, with 1 wherever that letter occurs in the pattern. For each text letter the whole state changes with two machine operations: "a shift and an AND". The shift extends every partial match by one position, and the AND keeps those where the new letter fits. All partial matches advance together, so no alignment is tried on its own. Shift-or is the same thing inverted: as Wu and Manber describe it, Baeza-Yates and Gonnet "used 0 to indicate a match and an OR operation instead of an AND".

Baeza-Yates and Gonnet could count mismatches only; Wu and Manber added insertions and deletions. For errors, keep k + 1 such rows. Row d holds the partial matches with at most d errors. Wu and Manber fill it from four cases: a matching letter from row d, and a substitution, a deletion or an insertion from row d − 1. That is a few more machine operations per row, and the rest stays the same.

Two limits follow. The state must fit in a machine word, or the work grows: "the discussion above assumes, of course, that the pattern's size is no more than the word size". And every text letter is processed. In exchange the time is steady: it "depends only on the size of the text (assuming again that the pattern fits into a word) and not on the actual text or the alphabet". Repeats do not hurt it.

Pattern CAT, text GCATCGT. Each row is one beginning of the pattern, and each column is one text letter. A 1 means "this beginning of the pattern ends here". The first three rows allow no error. The last three allow one.

Read the CAT rows. With no errors there is one hit: the exact word ends at the fourth letter. With one error the row shows that end and three others. The third letter gives CA, with the T deleted. The fifth gives CATC, with a C inserted. The last letter gives CGT, with A replaced by G. The machine does not say which error it was, only that some alignment ending here needs at most one.

We ran this recurrence against a plain edit-distance calculation on 20,000 random DNA pairs, and all 563,632 end positions agreed.

Bitap is not the only way to allow errors. If a pattern is cut into k + 1 blocks, then at most k errors cannot touch all blocks, so at least one block occurs exactly. A fast exact search for the blocks finds candidate places, and only those get the expensive check. Wu and Manber use this partition in agrep. It is the same logic as the seeds of s07.

What the programs really use

04Hashing: finding k-mers in constant time

Section 03 walked through the text with the patterns in hand. Hashing turns the problem around. Put the query k-mers in a table once, then ask of every k-mer in the data: "are you in my table?" If the table is built well, the answer takes about the same number of steps whether it holds a hundred k-mers or a hundred million.

Hash functions and hash tables

A hash function turns a key (here a k-mer) into a number. The same key always gives the same number, and different keys should give numbers that look random and spread evenly. A hash table is an array of numbered slots. To store a key, compute its hash, reduce it to a slot number, and write the key there. To look a key up, do the same calculation and go straight to that slot. Unless two keys compete for a slot (see below), nothing else in the table is read, and that is why the size of the set hardly matters.

Simple explanation with examples: a specimen cabinet with 64 drawers

Imagine a cabinet of 64 drawers and a fixed rule that turns any catalogue label into a drawer number. To file a specimen, apply the rule and open that drawer. To ask "do we have this specimen?", apply the rule and open the same drawer. You never walk along the cabinet reading labels.

Sooner or later two labels point to the same drawer. That is a collision, and it does not mean the two specimens are the same. So the drawer must keep the full label, and you must compare it with the one you hold. A hash table that stores the whole key, as this one does, can therefore answer exactly. The rest of this section is about what to do when the drawer is already taken.

Turning a k-mer into a number: 2 bits per base

DNA has four letters, so two bits are enough for a base: A = 00, C = 01, G = 10, T = 11. A k-mer becomes one whole number with no information lost, and it can be turned back into letters.

GATTA 10 00 11 11 00 = 572 TAATC 11 00 00 11 01 = 781 (its reverse complement)

This code has two useful properties. The complement of a base is 3 minus its code (A 0 ↔ T 3, C 1 ↔ G 2), so a program can build the other strand with arithmetic. And the numbers sort in the same order as the letters, so the canonical k-mer of lesson 1, the alphabetically first of the pair, is simply the smaller of the two numbers: 572, GATTA. Storing only canonical k-mers means a read matches whichever strand it came from. With odd k no k-mer is its own reverse complement (lesson 1).

At 2 bits per base, a k-mer of k = 31 takes 62 bits and fits in one 64-bit computer word; k = 32 is the limit for one word. A base such as N has no 2-bit code, so a program must treat it separately. ntHash, for example, skips every k-mer that contains a letter other than A, C, G, T or U.

Why not use the 2-bit number itself as the slot number? For small k you can: k = 12 needs 412, about 17 million slots. For k = 31 it would need 431, about 4.6 × 1018, nearly all empty. So the number must be squeezed into a table of practical size. Keeping only its last 6 bits would give 64 slots, but those bits are just the last three bases: every k-mer ending in AAA would fall in slot 0, and low-complexity sequence would pile up. This is why a hash function must mix all the bits before the slot is chosen.

Linear probing has one weakness. Full slots join up into runs, and any key that lands anywhere in a run must walk to its end, then make the run one slot longer. Long runs therefore grow faster than short ones. This is called primary clustering. Simple explanation with examples: why the plot bends so sharply

When the table is half full, a new k-mer has an even chance of hitting a free home slot at once, and runs of full slots are short. At 90 % full, nearly every home slot is taken and the free slots are few and far apart, so a k-mer may walk a long way to reach one.

The lesson for a real program: give the table more slots than it has keys. Memory spent on empty slots buys speed. Doubling the slots of a 90 % full table takes it to 45 %, and by the formula above the expected probes for an absent k-mer fall from about 50 to about 2.

Rolling: the next k-mer almost for free

Consecutive k-mers of a read share k − 1 bases. Computing each one from scratch repeats nearly all the work. A rolling calculation updates the previous value instead. With the 2-bit code this takes one shift: push the bits two places left, drop the base that left, add the base that came in. The reverse strand rolls the other way at the same moment, so both strands are ready without ever writing out a reverse complement.

forward GATTA 10 00 11 11 00 = 572 ATTAC 00 11 11 00 01 = 241 shift left, add C (01) at the end reverse TAATC 11 00 00 11 01 = 781 GTAAT 10 11 00 00 11 = 707 shift right, add G (10) at the front canonical of ATTAC = the smaller of 241 and 707 = 241

The same idea can apply to the hash value itself. ntHash (Mohamadi et al. 2016) gives each base a fixed random 64-bit number, its seed, and updates the hash of a k-mer in a few operations whatever k is:

H(next k-mer) = rotate(H(this k-mer), 1) ⊕ rotate(seed of leaving base, k) ⊕ seed of entering base

The value is a 64-bit hash for any k, so k is not limited to 32. It also keeps a second value for the reverse strand; the current code (version 2.4.0) adds the two to get one canonical hash, the same for both strands. Further hash values for a k-mer come from a few more operations on the first one, which suits Bloom filters. In the paper's test with multiple hash values for 50-mers in 250-bp reads, ntHash was over 20 times faster than the next best function. One difference from the 2-bit code: a hash cannot be turned back into the k-mer, and two k-mers can share it. A table that must answer exactly still has to compare the keys themselves.

A Bloom filter in front of the table

When the query set is small and the data are large, most k-mers in the reads are not in the set. The table must still be asked each time, and a large table does not fit in the cache, so each probe may be a slow trip to main memory. A small Bloom filter (lesson 2, section 03) can stand in front of it. Bloom's 1970 paper was about just this: cutting the space and the time needed to reject a non-member, in exchange for a small rate of false "yes" answers. A "no" from the filter is certain, and the table is not touched. A "yes" goes on to the table, which compares the real key. So the pair still gives exact answers, because the filter's false positives stop at the table.

A standard Bloom filter has one weakness in memory. Its h bits lie anywhere in a large array, so a positive answer or an insertion costs h cache misses. (A negative answer stops at the first 0 bit: under two misses on average, when the filter is tuned to have half its bits set.) A blocked Bloom filter (Putze, Sanders and Singler 2007) splits the array into small filters, each the size of one cache line; the paper gives 64 bytes, or 512 bits, as a common size. The first hash picks the block and the other hashes set or test bits inside it, so each operation costs one cache miss.

standard ...1..........1..................1..... h places, far apart blocked [........][.1..1..1][........][........] first hash picks the block

The price is accuracy. Chance loads some blocks more heavily than others, and the crowded blocks give more false positives. At 8 bits per element with 512-bit blocks the paper reports a false-positive rate of 0.0231 instead of 0.0215, which one more bit per element makes up. At 20 bits per element and 14 hash functions the rate almost triples. In the paper's own tests, on the hardware of the time, the blocked variants beat the standard filter for positive queries and insertions, by a factor close to 4 at best, and that best case used 32 % more memory.

05Worked example: scfish2

The last section gave the parts: 2-bit k-mers, a hash set, a Bloom filter. Here they work together in one real program. scfish2 is a lab tool, not yet public, about 300 lines of C. Its story has a twist: once matching became fast, matching stopped being the problem.

The job

When we close gaps in an assembly from short reads, we first need the reads that lie next to each gap. We pick anchors: 20-base words that occur only once in the genome and sit close to a gap, several on each side. A read pair that holds an anchor probably comes from that spot. So the question is plain: which read pairs of a whole library contain any of these exact words, on either strand?

The size is what makes it hard. The test library is public: SRR13862646, Galemys pyrenaicus, 84,051,642 read pairs of 151 bases, 14.2 GB as gzip files and about 57 GB unpacked. A 151-base read holds 132 words of 20 bases, so one pass means about 22 billion k-mers to check. Almost none of them is an anchor. The tool must therefore be very good at saying "no".

The usage line from the source file shows the whole interface:

scfish2 [-t threads] [-b batch_pairs] anchors.txt R1.fq[.gz] R2.fq[.gz] OUTPREFIX

It writes the matching pairs to two FASTQ files and their names to a list. If either read of a pair holds an anchor, both reads are kept.

Step 1: letters become a number, one base at a time

The anchors are stored as 2-bit codes: A = 0, C = 1, G = 2, T = 3, so a word of up to 32 bases fits in one 64-bit number. The read is then scanned once, base by base. Nothing is cut out or copied. Two numbers are kept up to date: f for the word as read and r for its reverse complement. These are the actual lines:

int c = code[(unsigned char)s[i]];
if (c < 0) { len = 0; f = r = 0; continue; }
f = ((f << 2) | (uint64_t)c) & kmask;
r = (r >> 2) | ((uint64_t)(3 - c) << shift);
if (++len >= K && has(f < r ? f : r)) return 1;
  • Line 2: any letter that is not A, C, G or T (usually N) restarts the count, so no word is ever built across it.
  • Line 3: shift the old word two bits left, add the new base, and drop the oldest base with the mask.
  • Line 4: the reverse complement grows from the other end. Complementing is just 3 - c, because A+T and C+G both add up to 3.
  • Line 5: f < r ? f : r takes the smaller of the two, the canonical form. One lookup now covers both strands. The read stops at its first hit, because one anchor is enough.

Each new base costs a few arithmetic operations, however long the word is.

Simple explanation with examples: rolling a 4-base word along a read

Take k = 4 and the read GATTC. In binary, A = 00, C = 01, G = 10, T = 11.

GATT f = 10 00 11 11 = 143 reverse complement AATC: r = 00 00 11 01 = 13 canonical 13 ATTC f = 00 11 11 01 = 61 reverse complement GAAT: r = 10 00 00 11 = 131 canonical 61

To go from the first line to the second, nothing is recomputed. f moves two bits left, the leading G falls off, and the new C (01) comes in on the right. r moves two bits right, and the complement of C (G, 10) comes in on the left.

If the same DNA were read from the other strand, GAAT would give f = 131 and r = 61. The smaller number is again 61, so both strands find the same entry.

Step 2: an exact set, then a filter in front of it

The anchors go into an open-addressing hash set. It is one plain array of 64-bit numbers with at least twice as many slots as anchors, so at most half of it is full. A key that lands on an occupied slot moves to the next one. The array stores the full code of each anchor, not a shortened fingerprint, so a "yes" from it is always true.

The trouble is memory. For 792,638 anchor lines the array takes 16 MB, and each lookup jumps to a random place in it. The lab notes describe this table as beyond the processor's fast cache. So a Bloom filter stands in front. It is a blocked one: each anchor sets 3 bits inside a single 64-bit word, so testing a k-mer costs one memory read, not three. For the same anchors the filter takes 2 MB. The source comment says that it "mostly stays in L2 cache".

static inline int has(uint64_t key) {
    uint64_t h = bmix(key), b = bbits(h);
    if ((bloom[h & bmask] & b) != b) return 0;
    uint64_t i = h64(key) & tmask;
    while (tab[i] != EMPTY) { if (tab[i] == key) return 1; i = (i + 1) & tmask; }
    return 0;
}

Line 3 is the whole trick. If even one of the three bits is empty, this k-mer was never stored, and the function leaves at once. Only the rest reach the hash set in lines 4 and 5.

Step 3: threads and batches

Each read can be checked without knowing anything about the others, so the work splits easily over threads. scfish2 works in batches of 500,000 pairs. Two threads read the batch, one for R1 and one for R2. Then all threads scan it, taking 4,096 pairs at a time as they become free:

#pragma omp parallel for schedule(dynamic, 4096)
for (size_t i = 0; i < n1; i++)
    hit[i] = (uint8_t)(scan(b1.arena + b1.seq[i], b1.slen[i]) || scan(b2.arena + b2.seq[i], b2.slen[i]));

The first line is an OpenMP instruction. Threads need no locks here: the set and the filter are only read during the scan, and each thread writes only its own places in hit[]. Afterwards the main thread walks through hit[] from the start and writes the matching pairs, so the output is in input order however the threads were scheduled.

Step 4: reading FASTQ directly

The earlier version, scfish, had the same matcher but ran behind a shell fan-out. paste joined each pair into one long line and a single awk dealt the lines out to the matcher processes. Every byte passed through that one line. scfish2 removes it. It reads the two FASTQ streams itself, takes every 4 lines as one record, and scans only line 2, the sequence. A .gz file is handed to an outside decompressor:

const char *dec = getenv("SCFISH_DEC"); if (!dec || !*dec) dec = "rapidgzip -d -c -P 4";
char cmd[8192]; snprintf(cmd, sizeof cmd, "%s '%s'", dec, p);

popen starts that program as a separate process and gives scfish2 its output as if it were a file. So decompression gets its own cores, and the tool can be pointed at whichever decompressor a server has. If R1 and R2 ever differ in record count, it stops with an error.

Why the results stay identical to grep

A speed-up is worthless if the answer changes. Here it should not change, for four reasons:

  • The filter never says a wrong "no". Every stored anchor set its own bits, so a real anchor always passes. A false alarm only costs one extra lookup.
  • The set is exact. It holds the full code, so a false alarm gets rejected there.
  • The code loses nothing. Two different words of up to 32 bases never share a 2-bit code. Two words share a canonical code only if they are the same word on opposite strands.
  • All anchors have one length. A fixed string of k letters is inside a read exactly when one of the read's k-mers equals it. The tool refuses a file with mixed lengths.

This was also tested, not just argued: on the whole library, grep, scfish and scfish2 all returned 13,029 pairs, with the same pair names. Two differences remain, and both matter if you repeat this:

  • Strands. grep -F matches only what is in the pattern file, while scfish2 always matches both strands. The results agreed because the file listed both. On a test subset that held one strand of many anchors, grep found 304 pairs and scfish 570.
  • What is searched. grep also searches read names and quality lines. scfish2 searches only sequence. No pair was found that way in these tests, but it could happen.

06Alignment as scoring

Everything so far looked for letters that agree exactly. Real homologous sequences do not agree exactly: bases have changed, and pieces have been lost or gained. To compare such sequences we stop asking "is this string here?" and ask "how good is the best way of lining these two up?". That question has a number as its answer: a score. This section shows how the score is defined, how a program finds the best one without trying every possibility, and how to tell a good score from a lucky one.

What an alignment and a score are

An alignment writes two sequences one above the other, with dashes where one has no letter opposite the other. Each column is a claim: these two letters descend from the same ancestral position, or (at a dash) a piece was inserted in one sequence or deleted from the other. A score adds up the columns: points for a match, a loss for a mismatch, a larger loss for a gap. The alignment with the highest score is called optimal. It is optimal only for those scores. It is a hypothesis about history, not an observation.

A G C C A U U G | | | | . | B G C C - U C G 5 matches, 1 mismatch, 1 gap of length 1

Before scoring: the dot plot

The oldest way to compare two sequences needs no scores at all. Put one sequence along the top and the other down the side, and mark every position where they agree. This is a dot plot: EMBOSS, a standard free package, calls it "an intuitive graphical representation of the regions of similarity between two sequences". Single letters agree by chance one time in four, so the plain plot on the left below is mostly noise. Asking for a run of agreeing letters removes the noise. Global alignment: Needleman-Wunsch

In 1970 Needleman and Wunsch set out the two-dimensional array and a way to find the best pathway through it. Their "maximum match" was the largest number of amino acids of one protein that can be matched with those of another "allowing for all possible deletions", and they already allowed a penalty, "a number subtracted for every gap made". Smith and Waterman later described it as the work that "first introduced an iterative matrix method of calculation".

The idea, in the form it has today, is dynamic programming: fill a table in which each cell holds the best score of aligning the two sequences up to that point. The number of possible alignments is astronomical, but no cell needs to know about them. The last column of any alignment can only be one of three things, so each cell looks at its neighbours and takes the best of three:

H(i,j) = the largest of:
  H(i−1,j−1) + s(ai,bj)  (two letters in one column)
  H(i−1,j) − gap  (a letter of A opposite a dash)
  H(i,j−1) − gap  (a letter of B opposite a dash)

Here H(i,j) is the cell for the first i letters of A and the first j letters of B, and s is the score of putting those two letters in one column. Global alignment means both sequences are aligned from first letter to last, so the answer sits in the bottom right corner. To read the alignment itself, walk back from there, each time to the cell the value came from. This walk is the traceback. The time needed is proportional to the product of the two lengths (Pearson 2013): double both lengths and the work grows four-fold.

Global alignment suits sequences related along their whole length, such as two alleles of a gene. It suits a search badly. A 300-bp SINE copy inside a 100-kb contig is not related to the rest of the contig, and forcing the two ends together only buries the real signal under gap costs.

Local alignment: Smith-Waterman

Smith and Waterman (1981) asked for something else: "a pair of segments, one from each of two long sequences, such that there is no other pair of segments with greater similarity". Their whole paper is three pages, and the change to the method is small. A fourth option joins the other three: zero.

H(i,j) = the largest of:
  H(i−1,j−1) + s(ai,bj)
  best gap from above
  best gap from the left
  0

Zero means: whatever came before was not worth keeping, start a new alignment here. The first row and column are all zeros, so an alignment may start anywhere for free. The traceback starts from the largest value anywhere in the table, not from the corner, and stops at the first zero. Everything outside that path is simply left out.

Simple explanation with examples: why a table finds the best of millions of alignments

Think of a walk through a mountain range, from any valley to the highest point you can reach, where each step adds or takes away height. You want the best route. You do not need to list all the routes. For each crossing you only write down the best height anyone can have on arrival, because a route that arrives lower can never overtake a route that arrives higher on the same crossing. Everything after the crossing is the same for both.

Each table cell is such a crossing. In the first example, the cell at row G, column G (the 10th row, the 8th column) looks back and sees that the cell on its diagonal holds 7. G matches G, so 7 + 3 = 10. Nothing else offers more, so the cell keeps 10. Nothing in the table is higher, so this is where the best alignment ends.

The zero is the right to give up: if your height falls below sea level, forget the walk and start again from the next valley. This is why local alignment finds a good stretch inside two otherwise unrelated sequences.

Gap costs: why opening costs more than extending

One deletion can remove many bases at once, so a 10-base gap is not ten times less likely than a 1-base gap. Smith and Waterman allowed any gap weight Wk for a gap of length k, and their example already used 1 + k/3. A cost of this form, a fixed charge for opening plus a smaller charge per letter, is called an affine gap cost. Altschul's tutorial at NCBI says such costs "have generally proved among the most effective", and also that there is no theory behind the particular numbers: gap scores "have been selected over the years by trial and error". Pearson (2013) agrees: "we do not have an analytical model for gap penalties".

Trying every gap length at every cell, as their equation is written, makes the table much slower to fill. With affine costs it is not necessary. Each cell also remembers the best score that ends in a gap from above and the best that ends in a gap from the left, and extending that gap by one letter is a single subtraction. The page's table works this way, and so does the inner loop of ssearch36 (its source keeps these as E and F next to H). Both ways gave identical cell values in our test of 2,000 random pairs.

Conventions differ, so read the manual before you copy numbers between tools. In FASTA36 the options are -f (opening) and -g (each residue), and the DNA defaults of −12 and −4 charge a gap of k bases 12 + 4k. A single-base gap therefore costs 16, more than three matches earn.

Substitution scores: what the numbers mean

Match and mismatch scores look arbitrary, but they are not. Altschul showed that the scores of any matrix with a negative expected score can be read as a log-odds ratio: the logarithm of how often a pair of letters occurs in true alignments, divided by how often it would occur by chance. A positive score means "more likely in related sequences than by chance". Pearson (2013) gives this protein example: in BLOSUM62, whose unit is half a bit, aspartate opposite aspartate scores +6, so this pair is 23 = 8 times more likely because of homology than by chance. Aspartate opposite leucine scores −4, so that pair is 4 times more likely by chance. The two common protein matrices are BLOSUM62 (default of BLASTP) and BLOSUM50 (default of FASTA and SSEARCH for proteins).

Two consequences matter in practice. First, the expected score of a random pair has to be negative. If it is positive, says Pearson, "the alignment will extend to the ends of the sequences, and be global, rather than local". Try it: set mismatch to −1 and match to 5 above, and watch the warning. (The 1981 example sits exactly at zero by design: its authors chose scores whose average for random sequences is zero.) Second, every pair of scores silently states how similar it expects the sequences to be:

For sequences that code for protein, compare proteins if you can. Pearson (2013) puts DNA:DNA look-back at 5 to 10 times shorter than protein:protein, and rarely more than 200 to 400 million years. Altschul's tutorial gives the same warning. Non-coding DNA such as a SINE has no such option, which is why the choice of DNA scores matters there.

Is the score good? E-values

A score of 300 means nothing alone: it depends on the scoring system and on how much sequence was searched. Altschul compares a raw score without its scoring system to "citing a distance without specifying feet, meters, or light years". We need to know what chance would produce.

A local alignment score is a maximum over a huge number of possible alignments, and maxima of many random values do not follow the normal bell curve. They follow an extreme value distribution, with a long tail on the high side. Karlin and Altschul (1990) gave the formulas for local alignments without gaps. The E-value of a score S, for sequences of lengths m and n, is the number of alignments at least this good expected by chance alone:

E = K · m · n · e−λS

Altschul explains why this has to be the shape. Double the length of either sequence and you double the places where a chance alignment can occur, so E doubles. To reach score 2x an alignment must reach x twice in a row, so E falls exponentially as the score grows. λ and K are just the natural scales of the scoring system and of the search space. Removing them gives the bit score, which can be compared between scoring systems:

S′ = (λS − ln K) / ln 2     E = m · n · 2−S′

So every 10 extra bits make a hit about 1,000 times less likely to be chance (Pearson 2013). The chance of at least one such hit, the P-value, is 1 − e−E, which is nearly equal to E when E is small. Here is what that means for a 300-bp query against both strands of a 3-Gb genome, so m·n = 300 × 6×109:

How to read an E-value without fooling yourself.
  • It depends on the search. The same score found in a database 100 times larger is 100 times less significant, although the two sequences have not changed (Pearson 2013).
  • DNA is harder. Pearson writes that protein hits with E < 0.001 can be trusted, while "DNA:DNA expecation [sic] values < 10−6 often occur by chance, and 10−10 is a more widely accepted threshold".
  • It works one way only. A significant score implies common ancestry. A non-significant score does not imply unrelated sequences.
  • The theory is proved only for alignments without gaps. Computer experiments strongly suggest that it holds with gaps too, but then λ and K must be estimated rather than calculated (Altschul's tutorial).
  • Regions of biased composition break the random model and can score high with no homology. Altschul's tutorial describes this for proteins. In DNA we expect the same from poly(A) tails and simple repeats (lesson 3, section 04).

ssearch36: the exhaustive reference

The program ssearch36 in W. R. Pearson's FASTA package (version 36.3.8) compares a query with every sequence of a library by "the Smith-Waterman algorithm". Nothing is skipped: no word has to match first, so a diverged copy with no exact word in common is still scored. That is the difference from the tools in the next section, and it is why ssearch36 is the reference against which you can measure what a faster tool misses.

# DNA query against a FASTA file; one line per hit, E-value and bit score included
ssearch36 -n -E 0.001 -m 8C query.fa library.fa

The cost is the table: every cell of query length times library length is filled, so a 300-bp query against both strands of a 3-Gb genome means about 2×1012 cells. Two things make this practical. Processor instructions that work on many cells at once speed the calculation up 10 to 20 times (manual page), and the FASTA guide puts ssearch36 at "only 2 - 5X slower" than the heuristic fasta36. Threads do the rest (-T).

Its statistics differ from BLAST's too. BLAST relies on λ and K estimated in advance for each scoring system. ssearch36 scores every library sequence, so it can fit the chance distribution from the scores of the search itself. That works only if most of the library is unrelated to the query: the guide says the routines "assume that the library contains a large sample of unrelated sequences". Where this fails, -z 11 fits the statistics to shuffled copies of the library instead.

Global relatives exist as well: ggsearch36 does a Needleman-Wunsch search in the same package.

In our projects. A SINE family breaks the assumption above: a genome is full of real copies of the query. Our public tool sear2k therefore runs ssearch36 with -z 11 on a genome cut into short windows. Lesson 7, section 02 explains the command option by option and shows why standard word-based tools miss old copies.

Exhaustive search answers "what is the best alignment?" with certainty, at a cost that grows with every base searched. For a whole library of reads, or a genome searched many times, that cost is too high. The next section keeps the scoring and the statistics, and looks at how to fill only the small part of the table that matters.

07Seed and extend: FASTA and BLAST

Smith-Waterman (s06) compares a query with every position of the data. That is safe, and slow. FASTA and BLAST save the time with a gamble: they align only where a cheap test says something is there. This section shows what the gamble wins, and which sequences it loses.

  1. Seed
    Find short stretches that are identical in query and subject. Such a stretch is a seed, also called a word or a k-mer (lesson 1). A lookup table makes this fast.
  2. Extend
    Grow an alignment outward from each seed, scoring as in s06, and stop when it stops paying.
  3. Score
    Keep what passes the reporting threshold (an E-value, s06).

Everything hangs on step 1. A region with no seed is never looked at. No later step can bring it back. Long seeds mean few places to check, so the search is fast but misses more. Short seeds mean many places to check, so it finds more but runs slowly.

FASTA: ktup and diagonals

FASTA came first (Lipman and Pearson, 1985; Pearson and Lipman, 1988). Its word size is called ktup. The current fasta36 uses ktup 6 for DNA by default; its guide says ktup 3 or 4 gives higher sensitivity.

The key idea is the diagonal: subject position minus query position. On a dot plot (s06) an ungapped alignment is a diagonal line, so all its seeds share one number.

query GATTACAGGCTA subject TTCCGGATTACAGGCTTAGC word GATTAC: query 1, subject 6 diagonal 6 − 1 = 5 word ACAGGC: query 5, subject 10 diagonal 10 − 5 = 5 same diagonal, same alignment

A chance word lands on a random diagonal. A real similarity piles up words on one. FASTA uses this in stages, which also explain the three scores in its output:

  • It finds all ktup words and keeps the best-scoring diagonal regions. The source keeps up to 10 per library sequence.
  • init1: the best region, rescored without gaps.
  • initn: regions joined into one chain, allowing gaps between them.
  • opt: a Smith-Waterman run only in a narrow band around the best diagonal. This is the score FASTA ranks by; the guide says the others can be ignored.

BLAST: words, X-drop, two hits

BLAST (Altschul et al., 1990) applied the same plan with a statistical base. For DNA its word list is simply every word of the query (the 1990 paper: "all contiguous w-mers in the query sequence, often with w = 12"). The list goes into a lookup table and the database is scanned past it. Protein BLAST also accepts similar words, not only identical ones; here we stay with DNA.

From each hit BLAST extends without gaps. The stopping rule is X-drop: walk outward and stop when the running score has "dropped more than X below the maximum score yet attained" (Altschul et al., 1997). The alignment then ends at the best point reached.

match +2, mismatch −3, X = 8 columns + + + + + x x x + + running 2 4 6 8 10 7 4 1 drop from 10 is now 9, more than 8: stop result alignment ends at the best point (score 10). The last two matches are never seen.

A piece that scores well enough without gaps then gets a gapped extension (s06's dynamic programming, also limited by an X-drop). The defaults in the BLAST+ source are in bits: 20 for the ungapped step, 30 for the gapped step (25 in megablast), 100 for the final alignment, and an ungapped piece needs about 27 bits to trigger gapping.

The two-hit method was added for proteins (Altschul et al., 1997): extend "only when two non-overlapping hits are found within distance A of one another on the same diagonal". One word is not enough, which saves many extensions and loses a little sensitivity. In BLAST+ for DNA it is off (-window_size 0) for blastn and megablast, and on with a window of 40 for dc-megablast.

Spaced seeds

A contiguous word has a hidden waste. Slide it one base and it shares 10 of its 11 positions with itself, so hits come in clumps: one long run gives many hits, and a region either has a clump or has nothing. PatternHunter (Ma, Tromp and Li, 2002) requires matches only at chosen positions and ignores the others:

contiguous, weight 11 11111111111 PatternHunter, 11 of 18 111010010100110111 1 = must match, 0 = ignored

The weight (the number of 1s) is still 11, so chance hits are as rare as before. Slid by one base, this pattern shares only 5 of its 11 positions with itself (our count), so hits are more independent of each other. For a 64-column region at 70 % identity, the inventors' patent gives 1.07 expected hits and a 0.30 chance of at least one for the contiguous word, against 0.93 expected hits and 0.466 for the spaced seed. Fewer hits on average, yet more regions found. Our exact calculation gives 0.300 and 0.467. In BLAST+ the idea is dc-megablast. Its default template is the "coding" one, 101101100101101101, which ignores every third position in most of its length; an "optimal" template and lengths 16 and 21 can be chosen. Remember that its default also needs two hits.

Simple explanation with examples: why word size decides nearly everything

Take a coin that lands heads 80 % of the time and toss it 250 times. Heads are bases that stayed the same in a 250-bp copy at 20 % divergence. A seed is a run of heads without a break.

A run of 11 heads turns up in 99.5 % of such series. A run of 28 heads turns up in only 8.5 %. Each extra toss in the run multiplies its chance by 0.8, and 17 extra tosses multiply it by about 0.02.

Why not then use very short runs? Because in a genome, short words occur everywhere by chance. Move the word size to 6 in the tool and read the line about the 1-Gb genome: each of those chance seeds is an extension the program must try.

  • Too little score. The threshold grows with the size of the search, while a short query has a small maximum score. High copy number does not by itself hide copies from BLAST, but it costs a lot. blastn has no rule that drops words frequent in the database (the -limit_lookup option belongs to the read mapper magicblast), so every copy produces seeds and every seed is extended. Output limits also matter: -max_target_seqs, default 100, counts subject sequences, not alignments. Other tools do drop frequent words, which is worse for repeats (s08, s09).

The misses are also not random. The chance of a hit falls with age and with shortness, so the copies you do get are biased towards young, long ones. Counts of copies, age plots and subfamily proportions then all carry that bias. This follows from the formulas above; we have not measured it in a BLAST run here.

08Indexing a genome

A scan reads the whole genome for every search. But a genome stays the same while you ask it millions of questions, one for each read. So arrange it once, the way a book has an index, and let each query go straight to the places that match. This section explains the two designs that real mappers use: the FM-index of bwa and bowtie2, and the minimizer hash table of minimap2.

The suffix array: every ending, in sorted order

A suffix is the piece of a sequence from one position to the end. A genome of n bases has n suffixes. Sort them alphabetically and keep only their start positions. That list of numbers is the suffix array. Every place where a word occurs is a suffix that begins with that word, so all those places sit next to each other in the sorted list. They form one interval of rows (Li and Durbin, 2009). Searching for a word now means finding its interval, and the numbers inside the interval are the answer.

The price is memory. Each position needs a whole number big enough to count to n: Li and Durbin give n⌈log2 n⌉ bits, or about 12 GB for the human genome. The bases themselves, at two bits each (section 04), need less than 1 GB. Most of what follows is a way of avoiding that 12 GB.

Simple explanation with examples: a suffix array is a dictionary of endings

Take the sequence ACAACG and add $, a mark for "end of sequence" that sorts before every letter. Count positions from 0. Here are its seven suffixes, sorted:

row  start  suffix
 0     6    $
 1     2    AACG$
 2     0    ACAACG$
 3     3    ACG$
 4     1    CAACG$
 5     4    CG$
 6     5    G$

Look for the word AC. Rows 2 and 3 begin with it, and no other row does, because sorting puts them together. Their start numbers, 0 and 3, are the two places where AC occurs. In a dictionary you do not read every page to find a word. You open the book in the middle and go left or right. The same works here, however long the list is.

The Burrows-Wheeler transform: the same letters, in a searchable order

Write the sequence, with its $, as a ring. Cut the ring at every position to get all its rotations, and sort them. The rows come out in the same order as the suffix array. The Burrows-Wheeler transform (BWT) is the last column of this table: for each suffix, the single letter that stands just before it in the genome. Li and Durbin's example: the BWT of googol$ is lo$oogg.

The BWT contains exactly the letters of the sequence, only in a different order, so it needs no more space than the sequence. It was first made for data compression (Langmead et al., 2009). Three facts make it useful for search:

  • It can be undone. The original sequence can be rebuilt from the last column alone.
  • The first column costs almost nothing. It is just all the letters in sorted order, so a table of a few counts describes it. Call this table C: C(a) is the number of letters, counting the $, that sort before a.
  • Equal letters keep their order. This is the last-first rule: "The ith occurrence of character X in the last column corresponds to the same text character as the ith occurrence of X in the first column" (Langmead et al., 2009). The third A in the last column is the third A in the first column.

Backward search: read the word from its last letter

The last-first rule gives a search that needs neither the suffixes nor the sorted table. Start with the last letter of the word: its interval is the block of rows that begin with that letter. Then add the letter before it. Among the rows of the interval, the ones with that letter in the last column are the places where the longer word occurs, and the last-first rule says where they land. Only two things must be known: C(a), and Occ(a, i), the number of times a occurs in the first i rows of the last column.

new start = C(a) + Occ(a, start)
new end   = C(a) + Occ(a, end)

Here the interval means the rows from start up to, but not including, end. (Li and Durbin write the same result with both ends included.) If start equals end, the word does not occur. Each letter costs two lookups, whether the genome has a thousand bases or three billion, so the time depends on the length of the word and not on the size of the genome. This is backward search. Li and Durbin credit the proof to Ferragina and Manzini (2000).

Simple explanation with examples: why start from the end of the word?

To find ACA, begin with the rows that start with A. That is one block. Now you want the rows that start with CA. Each row in your block tells you, in its last column, which letter stands just before it in the sequence. So the rows with a C there are the places where CA occurs. They jump to the C part of the table, and because equal letters keep their order they stay together as one block. To find where that block starts, you only count how many Cs lie above your block. Repeat with A. Each step makes the word one letter longer on the left, and the block can only stay the same size or shrink.

In the tool above, try the word GAT, and then GATC. The second word does not occur, and the search stops after two letters, because no T stands just before a C. A scan would have read the whole sequence to learn the same thing.

From the toy to bwa and bowtie2

The tool above keeps the whole table. A real FM-index keeps the BWT plus thinned-out helpers, and computes the rest when needed.

  • Counts. Storing Occ for every row would be huge. bwa stores it at every 128th row and counts the rest directly in the BWT (Li and Durbin, 2009; OCC_INTERVAL in the bwa source).
  • Positions. An interval tells you how many hits there are, but not where. bwa stores only every 32nd suffix array value. For any other row it walks with the last-first rule until it reaches a stored row, and adds the number of steps taken. bowtie2 has the same design: --offrate defaults to 5, which marks every 25 = 32nd row, about 340 MB for the human genome according to its manual.
  • Both strands. bwa builds its BWT from the genome and its reverse complement together (source code, bntseq.c). bowtie2 searches the read and its reverse complement instead. It also keeps a second index of the genome written backwards, the .rev files. Bowtie 1 introduced this mirror index to limit wasted effort when it tries substitutions in a read (Langmead et al., 2009).

Backward search finds exact matches only, and reads have errors. So neither program searches for a whole read. They use the seed-and-extend plan of section 07, with the FM-index as the seed finder. bwa mem starts from SMEMs; its author says the method "essentially finds at each query position the longest exact match covering the position" (Li, 2013). So its seeds have no fixed length. bowtie2 cuts seeds from the read and aligns them with the FM-index. Its manual is open about the cost: this step gives speed "at the expense of missing some valid alignments". How these programs turn seeds into results is the topic of section 09.

A hash index: look the word up directly

The other design uses the hash table of section 04. The key is a k-mer, and the value is the list of places where that k-mer occurs. One lookup returns all the places at once, whatever the genome size. But a table of every position of a genome is large, because each position must be written down. One old fix is to store only every w-th position of the target and to look up every k-mer of the query; BLAT does this (scheme as described by Li, 2016). The index shrinks, but the query saves nothing: it must try all its k-mers, because it cannot know which ones were stored.

A better fix is a rule for keeping k-mers that depends only on the sequence itself, and not on where you start reading. Then a read and the genome keep the same k-mers wherever they share a stretch, and both sides become small.

Minimizers: keep the smallest word of each window

That rule is the minimizer (Roberts et al., 2004); winnowing, from document copy detection, is the same idea (Schleimer et al., 2003). In the words of the minimap2 manual, "A minimizer is the smallest k-mer in a window of w consecutive k-mers." This is how minimap2 applies the rule:

  1. Take one form for both strands.
    Each k-mer is compared with its reverse complement and the smaller of the two is used (the canonical k-mer of section 04), so both strands give the same word. A k-mer equal to its own reverse complement is skipped, because its strand cannot be told.
  2. Scramble the order.
    "Smallest" does not mean first in the alphabet. If it did, runs of A would always win, and they are common and tell you little (Li, 2016). A hash function turns each k-mer into a number, so "smallest" becomes an arbitrary but repeatable choice.
  3. Slide the window.
    In every w consecutive k-mers, keep the one with the smallest hash. Neighbouring windows usually pick the same k-mer, so far fewer k-mers are kept than there are windows. If two k-mers tie, both are kept.

Two numbers tell you what this buys. The density is the share of k-mers that are kept: for random data it approaches 2/(w+1) (Schleimer et al., 2003). With minimap2's defaults, k = 15 and w = 10, that is about 18 %. The guarantee is that an exact match of at least w + k − 1 bases always shares a kept k-mer, because both copies contain the same whole window. For the defaults that is 24 bases. Shorter matches may or may not be seen. Noisy reads have few long exact stretches, so some parts of a read give no seed at all, and the next step must cope with such gaps.

Simple explanation with examples: why two observers mark the same animal

Animals stand in a very long line. The rule: in every group of 10 neighbours, mark the lightest. Two observers each see only a part of the line. Where their views overlap by at least 10 animals, they share a whole group, so they mark the same animal there, without ever talking to each other. Each one has written down only a small part of the line, and yet they can line up their notes on the shared marks.

Marking every 10th animal instead would fail: if the second observer starts one animal later, their marks never meet. That is the problem with storing every w-th position. Minimizers are the "lightest animal" rule, with a hash value as the weight.

Chaining: from scattered matches to one place

minimap2 "indexes them in a hash table, with the key being the hash of a minimizer and the value being a list of locations of the minimizer copies" (Li, 2018). For each read it computes the read's own minimizers and looks them up. Each hit is an anchor: this stretch of the read matches that stretch of the reference. (The word is used differently in section 05, where an anchor is a chosen unique word next to a gap.) Most anchors of a real read lie along one diagonal, with small sideways steps at insertions and deletions. Chance matches and repeats land elsewhere.

A chain is a set of anchors in the same order on both sequences. minimap2 finds the best ones by dynamic programming, the method of section 06, but it works on a few anchors and not on every base. For each anchor it looks at earlier anchors and takes the one that gives the best score: matching bases gained, minus a cost that grows with the size of the gap (Li, 2018). A read can be placed from its chain alone. By default minimap2 reports only that, so its coordinates are approximate. Only with -c or -a does it add a base-level alignment (README).

Very common minimizers are thrown away first: by default the top 0.0002 fraction of the most frequent ones (-f). For mapping this is a gain, because a read has many other seeds: "we can afford to skip highly repetitive seeds without affecting the final accuracy" (Li, 2018). For a search for repeat copies it is the opposite, because all minimizers of a repeat are common. The README of the lab tool sear reports a test with a 6-kb L1 on human chromosome 21: indexing the genome found 4 of the 73 full-length copies, and indexing the query and streaming the genome past it found 65 (sear2k; see also lesson 7, s02).

09Mappers in practice

A mapper takes millions of short or long reads and puts each one at a place on a reference genome. It is the machinery of seed and extend and of the genome index packaged into one command. This section shows the four mappers you will meet most often, the commands that run them, what they write, and the one number that tells you how much to trust each placement. The last part shows what repeats do to that number.

Mapping is searching, many times

In the earlier sections one query was searched in one genome. A mapper does the same for every read of a sequencing run, so speed matters, and the genome index is built once and reused. For each read it answers three questions: where does it go, how well does it fit, and is there another place where it fits almost as well. The third question is what makes repeats hard (below). The mapped reads are what the later lessons use: coverage and heterozygosity in lesson 4, methylation calls in lesson 6, and copies of a SINE or satellite in lesson 7, section 02.

Mapping quality: how sure is the placement

MAPQ is a whole number per alignment. The SAM specification defines it as −10 log10 of the probability that the mapping position is wrong, rounded to the nearest integer, and says that 255 means "not available". The Bowtie 2 manual gives the reading rule: a MAPQ of 10 or less means at least a 1 in 10 chance that the read truly came from elsewhere. The same manual explains where it comes from: the bigger the gap between the best alignment's score and the second-best alignment's score, the more unique the best alignment, and the higher its MAPQ should be.

Two points keep you out of trouble.

  • Each program computes its own MAPQ. bwa mem uses a formula of the score gap, the read length and the identity. minimap2 uses chaining and alignment scores and also the length of the read covered by repeated seeds. Bowtie 2 looks the number up from a ladder of thresholds on the gap, so its values come in a few steps rather than a smooth range. A MAPQ of 30 from one tool is not a MAPQ of 30 from another.
  • It is an estimate made from what the program found. It cannot know about a copy that the search never reached, and a wrong place that fits better than the right one gets a confident wrong MAPQ (try it below).

The bwa formula is short enough to read. In bwa 0.7.19 (function mem_approx_mapq_se) with the default settings, for a read of length l with alignment score S and best other score S2 (at least 19 when none was found, the minimum seed length):

identity = 1 − (l×A − S) / (A+B) / l
f = identity² × (l < 50 ? 1 : ln 50 / ln l)
MAPQ = (int)( 6.02 × (S − S2) / A × f² + 0.499 ), kept between 0 and 60

with A = 1 (match score) and B = 4 (mismatch penalty); (int) drops the fraction, so adding 0.499 rounds to the nearest whole number. The real program then lowers it further for extra suboptimal hits and for the fraction of the read covered by repeated seeds; the toy below leaves both out and says so.

  • Secondary (0x100): an alternative place for the same read, as happens in repeats. Flag it to be sure not to count the read twice.
  • Supplementary (0x800): another piece of a split read, a chimeric alignment. A 10 kb long read crossing an inversion maps in two pieces, and each piece is a line.

What repeats do

A read from inside a repeat fits several places. Repeats are a large part of many genomes (lesson 3, section 02), and the young members of a repeat family are the most similar to each other. When two copies differ only at a few sites, a read has to cross one of those sites to tell the copies apart. A read that does not cross any has equal scores for both copies, a gap of zero, and so a MAPQ near zero. Longer reads, and reads that reach into the unique flanking DNA, escape the problem, which is one reason long reads place repeats better.

The tools also cut their effort on very repetitive seeds. bwa mem drops a maximal exact match that occurs more than 500 times (-c 500). minimap2 ignores the most frequent minimizers (-f 0.0002: the top 0.02 %). Bowtie 2 stops after 15 consecutive failed seed extensions (-D 15) and re-seeds at most twice (-R 2) in its default mode. Raising these limits costs time and helps reads that fit many places.

In practice, a MAPQ filter removes the reads of recent repeat copies. The Bowtie 2 manual gives the example of a variant caller that ignores alignments with MAPQ below, say, 10. That is sensible for variant calling, where a wrong placement can make a false variant. It is wrong for counting repeat copies, because it hides exactly the copies you wanted to count. Finding the copies is the job of the genome search in lesson 7, section 02, not of read mapping with a quality filter.

Simple explanation with examples: why a read in a repeat gets MAPQ 0

Imagine two shops that sell almost the same sweets. You find a receipt (the read) with only the list of sweets and no shop name. If the list uses only sweets both shops sell, the receipt fits both shops equally well and you cannot say where it came from. If one sweet appears in only one shop's range, the receipt fits that shop better.

locus 1 ...ACGTTGCATGGCA... locus 2 ...ACGTTGCACGGCA... read A ..GTTGCA fits both: gap 0, MAPQ near 0 read B ..GTTGCATGG fits locus 1 only: gap > 0, MAPQ rises

The mapper does what you did: it compares the best fit with the second-best fit. A big gap means “I am sure”, no gap means “it is a coin toss”. MAPQ is that confidence written as one number, where every 10 points mean ten times less chance of being wrong. A sequencing error can move a read from one shop to the other, which is why even a high MAPQ is only an estimate.

10Comparing whole data sets

Sections 02 to 09 asked where in a genome a sequence sits. A different question comes up just as often: how similar are these two data sets, and what is in this one? Are two read sets from the same animal? Does a read file hold bacterial or human DNA? How far apart are two assemblies? None of this needs an alignment. You cut each data set into k-mers (lesson 1) and compare the k-mer sets.

Simple explanation with examples: what "shared k-mers" means

Take two short sequences that differ by one letter at the end, and cut them into 3-mers (k = 3 only to keep the example small; real work uses 21 or more, and this toy skips the reverse-complement step):

A: ATGCGTAC → ATG TGC GCG CGT GTA TAC (6 different 3-mers) B: ATGCGTAA → ATG TGC GCG CGT GTA TAA (6 different 3-mers) shared: ATG TGC GCG CGT GTA = 5 all different k-mers: 5 + TAC + TAA = 7

The Jaccard index is the shared k-mers divided by all different k-mers: 5 / 7 = 0.71. It is 1 for identical sets and 0 for sets with nothing in common. In a real 21-mer comparison one substitution destroys up to 21 k-mers in each sequence, the 21 that cover that position, so the Jaccard index drops much faster than the divergence rises. The Mash distance below undoes this effect.

2. BBDuk: is any of this reference in my reads?

BBDuk (from the BBTools package) compares every read with the k-mers of a short reference, such as adapters, PhiX or a mitochondrial genome, and splits the reads into two outputs. In its default mode, a read with a matching k-mer goes to outm and the other reads go to out. The k-mer length is k=27 by default, and a reference shorter than k cannot be found. Two settings from the tool's own help decide what "match" means: minkmerhits (default 1, so one shared k-mer is enough) and maskmiddle (on by default: the middle base of each k-mer is a wildcard, so a read with a single sequencing error is still found).

bbduk.sh in=reads.fq.gz ref=mito.fa k=27 \
         outm=mito_reads.fq.gz out=nuclear_reads.fq.gz stats=stats.txt

BBDuk answers "does this read share a k-mer with that reference", and nothing more: there is no alignment and no position.

3. Kraken2: whose DNA is this?

When the reference is not one sequence but thousands of genomes, you want to know which genome a read belongs to. Kraken2 (Wood, Lu and Langmead, 2019; lesson 1 uses it to screen reads) solves this with a lookup table built once. For every k-mer in the reference genomes the table stores the lowest common ancestor of all genomes that contain it. To classify a read, Kraken2 looks up the read's k-mers and picks the branch of the taxonomy tree they point to. To save memory it stores and queries only a sample of the k-mers, their minimizers (section 08), in a compact hash table. The manual says this table can occasionally return a wrong answer (false positives in under 1 % of queries) and that confidence thresholds compensate. In the build step the default k-mer length is 35 and the minimizer length 31.

The --confidence option decides how many reads stay "unclassified", so it is worth understanding. The manual's own example: a read has 21 k-mers that could be looked up. Sixteen point to taxon 562 (13 and, later, 3 more), four point to its parent 561, and one is not in the database. The label 562 scores 16/21 = 0.76. The label 561 counts every k-mer in its clade, 16 + 4 = 20, so it scores 20/21 = 0.95. With --confidence 0.8 the read is moved up from 562 to 561, because 0.76 is below the threshold. Above 20/21 it would be unclassified. A higher threshold gives fewer, safer calls.

kraken2 --db $DBNAME --threads 8 --confidence 0.1 \
        --report k2_report.txt --output k2_reads.txt reads.fq

Check the database before you trust the answer. A read can only be assigned to a group that is in the database. The manual says the default database was 29 GB in January 2018 and needs slightly more than that in memory. Lesson 1 gives the rule that matters for zoologists: the Standard database has no fungi, and a vertebrate read set gives some hits to human or to relatives that are expected, not contamination.

4. Sketches: keep only the smallest hashes

Databases and Kraken2 still touch every k-mer. Mash (Ondov et al., 2016, Genome Biology 17:132) goes further: it replaces each data set by a sketch, a list of (by default) 1000 numbers, and compares data sets by comparing the lists. The idea in four steps:

  1. Hash every k-mer.
    A hash function turns each canonical k-mer into a number. The same k-mer always gives the same number, in whichever data set it occurs, and the numbers of different k-mers look random.
  2. Keep the s smallest.
    The sketch of a data set is its s smallest hash values (Mash defaults: s = 1000, k = 21). Because the numbers are random, these are a random sample of the data set's k-mers. This way of sampling is called MinHash ("minimum hash"), and Mash takes its name from it.
  3. Merge the two sketches.
    Merge the two sorted lists and stop after s different hashes have been seen. This gives the s smallest hashes of the union of both data sets, a random sample of it. Count how many of them are in both sketches. That fraction estimates the Jaccard index j (the Mash documentation writes j = |As ∩ Bs| / s).
  4. Convert Jaccard to a distance.
    With the Mash distance formula below.

Mash derives the distance from a simple model: every position mutates independently with probability d. A k-mer then survives untouched with probability e−kd, so the share of k-mers kept by both sequences is about e−kd. The Jaccard index j of two sets of similar size relates to that share by 2j/(1 + j). Solving for d:

D = −(1 / k) · ln( 2j / (1 + j) ) D = 1 when j = 0

Two examples at k = 21: j = 0.5 gives D = −ln(2/3)/21 = 0.019, about 1.9 % substitutions; j = 0.9 gives D = 0.0026. The authors present D as an estimate of the mutation rate. On 500 Escherichia genomes, with s = 1000 and k = 21, it matched 1 − ANI (average nucleotide identity) with a root-mean-square error (a typical error size) of 0.00274, for ANI between 90 and 100 %. They also state that the match degrades for more divergent genomes, because the variance of the estimate grows with distance, and that the formula "carries many assumptions": it does not model insertions, deletions or genes present in only one genome.

Three things to try. (1) Set the divergence to 8 % and the sketch size to 10, then press the new-sequences button many times: the estimated distance wanders far from the true one, and now and then no shared hash is found at all (j = 0, so D = 1). (2) At size 1000 the estimate stays close to the true value. The Mash documentation gives the error bound of an estimate for sketch size s as √(1/s), about 0.03 at s = 1000. (3) Raise the divergence towards 20 %: almost no 21-mer is left in common, the sketches share few or no hashes, and the estimate becomes unreliable. This is why Mash is used for genomes of one species or genus, not for distant ones.

Simple explanation with examples: why the smallest hashes are a fair sample

Imagine every different k-mer of the two data sets written on a card, and a stranger who gives each card a random number by a fixed rule, so the same k-mer always gets the same number. Lay all the cards in order of number and keep the first thousand. Those cards are a random sample of all k-mers, not the ones that "start with A" or follow any pattern, because the numbers are random.

Now do this separately for data set A and for data set B, with the same rule. A k-mer that is in both gets the same number in both, so it is either among the smallest in both lists or in neither. Merging the two lists and keeping the first thousand different numbers gives the thousand smallest of the union. The fraction of them that appear in both lists is the fraction of the union's k-mers that are in both: the Jaccard index, estimated from a sample of a thousand. A genome of billions of k-mers has become a thousand numbers.

Sketching reads. Reads carry sequencing errors, and each error makes new k-mers seen once. The Mash documentation says removing unique or low-copy k-mers usually improves results for read sets (-m 2 keeps k-mers seen at least twice) and that -r should be given so that genome size is estimated from the k-mers, not from the file length.

mash sketch -r -m 2 -k 21 -s 1000 -o reads_a reads_a.fq.gz
mash sketch -r -m 2 -k 21 -s 1000 -o reads_b reads_b.fq.gz
mash dist reads_a.msh reads_b.msh      # name, name, distance, p-value, shared hashes

FracMinHash sketching keeps a fixed fraction of all k-mers instead of a fixed number, which the README says allows accurate comparisons (including ANI) between data sets of different sizes. sourmash gather is a combinatorial k-mer approach for metagenomic profiling. 11Choosing the tool

Every method in this lesson answers the same trade-off: scan the data each time or build an index once, accept only exact matches or tolerate differences, be sure or be fast. The last skill is to look at the question and the size of the data and pick the smallest tool that can answer it. A search of a few kilobases against a small bank should take a second or less. If your plan takes minutes, the plan is probably wrong, not the computer.

Three questions before you run anything

  1. What exactly is asked? Write it in one sentence and do only that. "Where does this 400 bp sequence occur in these 30 contigs?" is a small question. "Map all reads to the genome" is a different question.
  2. How big is the data? Count the bases of the query and of the target. A few kb against a few thousand short sequences is tiny; one genome is large; a whole sequencing library is larger still.
  3. Does the answer already exist? An indexed BAM, a PAF file, a results table from an earlier run. Reuse it before computing it again.

Common mistakes

  1. Mapping a whole read set to find the reads of one locus.
    The reads were already mapped and indexed once. Asking for a region takes seconds with samtools view. In our lab, mapping the whole set again took many minutes and wrote a BAM of many gigabytes. If you do need to map, map only the extracted reads (section 09). Map each allele alone too: two near-identical alleles in one reference give the reads mapping quality 0, and the reads seem to disappear (lab notes).
  2. BLAST defaults on a short query.
    The default blastn task is megablast, whose word size is 28, so a 25 nt query cannot even form a seed. Use -task blastn-short (word size 7, reward 1, penalty -3, E-value threshold 1000, filtering off). The default also filters low-complexity sequence, which can mask a short repetitive query (section 07).
  3. An exhaustive aligner on the whole genome for a small question, or a fast heuristic where sensitivity matters.
    These are wrong in opposite directions. Full Smith-Waterman (ssearch36) is the reference for sensitivity, but you do not need to scan a genome to ask whether a 20-mer is in a 2 kb window (section 06). A seed-and-extend tool or a mapper, given short, diverged, high-copy queries such as an old repeat, misses copies (lesson 7, section 02).
  4. Searching one strand, or searching wrapped lines.
    grep reads lines and knows nothing about the reverse complement. Search the string and its reverse complement, and join the sequence lines of a wrapped FASTA first, or a match that crosses a line break is missed (section 02).
  5. Using coordinates from a table without checking them.
    Before mapping reads to a slice of an assembly, map the sequence you care about back onto the slice. It takes seconds and shows a wrong region, a shift of one between 0-based and 1-based counting (the first base called 0 in one file and 1 in another), or a different assembly version straight away (lab notes).
  6. Trusting a hit without asking what it hits.
    A best hit to an unrelated organism is not a classification. Look at the aligned length, the identity and the species before you name a sequence (section 10). And one correct control case does not prove that every other case ran: compare the read counts with the number you expect.
  7. Building an index for a search you run once.
    An index pays when the same target is searched again and again, or by very many queries (section 08). For one query against a small target, a scan is faster than the build. This is our reasoning from the methods in this lesson, not a rule from a manual.

Simple explanation with examples: a taxi, a bus, a railway

You can cross a town by taxi or by building a railway. For one trip of two streets, a taxi (a small scan) is right: no waiting, no cost to set up. If thousands of people go the same way every day, the railway (an index of the genome, built once) pays off. A railway for one trip is the mistake, and so is walking a thousand trips on foot.
