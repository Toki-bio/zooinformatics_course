02Finding copies of a known SINE

You have a consensus of a SINE (section 01), from a database or from your own work. Now you want every copy of it in a genome: where each copy sits, its sequence with a little of the DNA around it, and how many copies there are. This sounds like a routine search. For SINEs it is not, and the reasons decide which tool you use.

Why standard search tools miss SINE copies

SINE copies are a hard target for three reasons at once. They are short: the consensus sequences our lab searched in one rodent genome are only about 200 to 270 bp long. Short means a small maximum alignment score, so a match must be nearly perfect to look "significant". They are diverged: every copy has collected its own mutations since it was inserted, and old copies can differ from the consensus at 20-30 % of positions (see the repeat landscapes in lesson 3, section 04). And they are numerous: a successful family can have hundreds of thousands to millions of copies in one genome.

Good for annotating a genome; less suited when you want one family's copies with their flanks for your own alignments.

The way out is to drop the word step and compare the consensus with every position of the genome. That is the Smith-Waterman algorithm (Smith and Waterman, 1981): it finds the best local alignment between two sequences, scoring every match, mismatch and gap, without any shortcut. It is guaranteed to find the best-scoring match, and it is slow. The program ssearch36 from W. R. Pearson's FASTA package (version 36.3.8) runs it with fast processor instructions and adds statistics to every hit.

sear: the lab's search, step by step

sear2k is our lab's public Bash tool; its main script is called sear. It takes one consensus and one genome FASTA and runs ssearch36 on the genome cut into small pieces. SINEderella (section 08) runs it in its first step, once for each consensus. What follows is read from the script itself (repository commit 923ffb6, October 2026).

  1. Cut the genome into overlapping windows
    seqkit sliding -g -s 2000 -W 2500: windows of 2500 bp that start every 2000 bp, so neighbouring windows overlap by 500 bp. Any copy of up to 500 bp therefore lies whole inside at least one window (try it in the box below). The window file is about 1.25 times the size of the genome.
  2. Split the windows into 20 parts
    seqkit split2 -p 20. The parts are searched one after the other; the parallel work happens inside ssearch36, which uses all processor cores (-T).
  3. Search each part with ssearch36
    Both strands of every window are compared with the consensus. Output is a table, one line per hit: window name, percent identity, coordinates, E-value and bit score.
  4. Merge hits in a window and apply two rules
    Hits on the same strand of one window that touch or overlap are merged (bedtools merge -s). A merged hit is kept when the best identity in it is at least 65 % and its longest alignment covers at least 0.8 × the consensus length on the genome. Shorter (partial) copies are dropped, not shortened.
  5. Put the hits back on the chromosomes
    Each window's name ends in _sliding:start-end; sear adds that offset to the hit coordinates. A copy seen in two overlapping windows becomes one interval in a second merge.
  6. Write the results
    A 7-column BED file (chromosome, start, end, identity %, length, strand, bit score) and a FASTA of every copy with flanks of 50 bp on each side (--slop L,R sets other sizes). The files are named after the first three letters of the genome file and the query name, for example gen-dip.bed and gen-dip.bnk.

Three options change the search. -m (minus bank) cuts out every hit found in a part and searches what is left again, round after round, until a round finds nothing. Our reading of why this helps: ssearch36 reports further alignments in the same window only under a stricter E-value cut-off, so a second copy in a window can be left out of the first round. -b N also takes the N best hits by bit score and aligns them with MAFFT, the consensus as first row, for a quick look. Queries of 1000 bp or longer (LINEs, not SINEs) are switched automatically to minimap2 with the roles reversed: the query is indexed and the genome is streamed past it in windows.

Explain

Which window holds the whole copy?

Ten kilobases of a chromosome cut the way sear cuts it: 2500-bp windows every 2000 bp. Move a copy along and change its length. The rule that the longest alignment must cover 0.8 × the copy length is applied inside each window, before the windows are joined. The behaviour for long copies is our reading of the source code, not a documented feature. (Queries of 1000 bp or more go to minimap2 mode instead, so the slider stops below 1000.)

The ssearch36 command and what its options do

This is the exact call inside sear (the same in all three versions of the script in the repository):

ssearch36 -g -3 -T $THREADS -Q -n -z 11 -E 2 -w 95 -W 70 -m 8C query.fa part.bnk 3
-n, -Q
Treat the query as DNA; quiet mode (no questions asked).
-T $THREADS
Number of threads; sear uses $THREADS if you set it, otherwise all cores.
-m 8C
BLAST-like table with comment lines: query, window, % identity, alignment length, mismatches, gap openings, query start and end, window start and end, E-value, bit score. No alignments are printed, so -w 95 -W 70 (line width and context width of printed alignments) have no visible effect.
-E 2
Report hits with E-value below 2. This is also ssearch36's default for DNA. Note what the E-value is counted against: one part file, not the whole genome (no -Z, which would set the database size by hand).
-z 11
Estimate the statistics from shuffled copies of each window. Explained below.
trailing 3
The optional third argument of the FASTA programs is the word size (ktup). The guide says only the programs with "fast" in their name use it; Smith-Waterman uses no words.
-g -3
Our lab manual and the FASTA36 documentation read this flag differently, and we have not tested which reading is right, so we leave it unexplained here.

The scores: with its DNA defaults (source code of FASTA 36.3.8j1) ssearch36 gives +5 for a match and −4 for a mismatch, and charges a gap of k bases 12 + 4k. (sear passes its own -g -3, which may change the per-base part; see above.) A perfect 250-bp copy scores 1250. Random DNA also scores something: in the toy below, shuffled 420-bp windows reach roughly 50-100 against a 150-bp consensus, and in a whole genome the best chance scores are higher, because there are far more places to look.

Statistics need care: what -z 11 is for

An E-value needs a picture of what scores pure chance produces. By default (-z 1) ssearch36 builds that picture from the scores of the whole library it searched, which works when nearly all library sequences are unrelated to the query. The FASTA guide says so directly: the statistics "assume that the library contains a large sample of unrelated sequences", and if the library contains many related sequences, the parameters should be estimated with -z 11 to -z 15. A window bank of a genome full of SINE copies is such a library: a large share of the windows hold a real copy.

With -z 11, ssearch36 also scores a randomly shuffled copy of every window (same letters, order destroyed) and fits the chance distribution to those scores. The manual page warns that this means twice as many comparisons. Because the shuffles are random, E-values change a little from run to run, so hits close to the cut-off can appear in one run and not in the next. Two consequences: report counts as "about", and do not expect two identical runs to give identical files. The lab's assignment step (section 04) repeats its searches and uses exactly this wobble to keep only assignments that survive every repeat.

A second point is the size of the search. -E 2 means "fewer than two hits this good expected by chance in this part file". For a whole genome, each of the 20 parts can therefore let through a hit or two on score alone; the identity and length rules of step 4 are what removes them (our reasoning from the options, not a measured rate).

What the toy shows. Young copies score far above anything the shuffled windows reach. The oldest copies score close to the chance range, so any threshold trades missed copies against false hits, and the shuffled scores tell you where chance ends. (The chance count assumes every window were empty; a window that holds a copy reports the copy instead, so fewer false hits appear than the count suggests.) The identity and length rules remove false hits even at a low threshold, but they also remove the oldest copies and every copy that was cut short. With seeds of 28 bases only the young copies are aligned at all, whatever the threshold; seeds of 11 bring back most of the middle-aged ones, but not the oldest. The real blastn also extends hits from the seed instead of aligning the whole window, so in reality it is, if anything, less generous than this toy. Press "new toy genome" a few times: the same ages give different scores, because mutations fall in different places.

Simple explanation with examples: finding a misprinted phrase in a long book

Imagine a 3-million-page book in which a 250-letter advertisement was printed a million times, and every reprint added typos. A seed-based search is like using the index at the back: you look up one long exact word from the advert, and only open the pages where that word occurs. If every copy of that word has a typo, you never open the page.

advert (consensus): the quick brown fox jumps over the lazy dog old copy: the quack brawn fax jumps ovar thi lazy dug exact 11-letter words shared: none ("jumps over " is broken by "ovar") exact 5-letter words shared: "jumps", " lazy" ...

Smith-Waterman is reading every page and comparing it letter by letter with the advert, giving points for each agreeing letter and taking points away for each typo. Slow, but nothing is skipped. Cutting the book into overlapping 2.5-page pieces (the windows) means each piece holds at most one or two copies, so each copy gets its own score.

A rough sum for real copies: if 20 % of positions are mutated at random, a given run of 28 bases survives intact with probability 0.828 ≈ 0.2 %, so a 250-bp copy with about 220 such runs has well under one intact 28-base word on average. A run of 11 bases survives with 0.811 ≈ 8.6 %: about 20 intact words per copy. (Our arithmetic; real mutations are not perfectly random.)

Copy length: full-length and partial copies

A copy in the BED file is rarely exactly as long as the consensus. Small insertions and deletions change its length; the poly(A) tail is long in young copies and shortens over generations (Vassetzky et al. 2021, IJMS); and the alignment can stop a few bases short of the true end where the copy has decayed. The flanks are there so that you can see the real ends in an alignment.

More important is the 0.8 rule. A copy that is only partly present (cut at its 5′ end when it was inserted, broken by a later insertion or a deletion, or lying at the edge of a contig) is not extracted at all if its longest alignment covers less than 80 % of the consensus. So sear's count is a count of full-length or nearly full-length copies, not of every SINE-derived fragment. That is deliberate: the downstream steps align copies and compare their flanks, and fragments would break both. You can lower the rule (the third argument, Slf) to see fragments, but then two pieces of one broken insertion can count as two copies, and pieces of other families that share a part with your SINE (a common 5′ head, for example) start to match.

Counting copies

What you count is the number of loci: intervals left after all overlapping hits have been merged. Hits from two overlapping windows become one interval inside sear. When you search with several consensus sequences of one family (a bank: the family's subfamilies, see 04), the same copy is found by several of them. SINEderella's first step therefore merges the hits of all consensus sequences into one interval per locus before it counts (strand-aware), and removes loci inside known satellite regions (06). Whenever you quote a copy number, quote the rules with it: which consensus sequences, which identity and length cut-offs, merged how. "1.2 million copies" means little without them.

Two more things limit any count. First, a copy can only be found if it is in the assembly: young, nearly identical copies are the ones assemblers collapse or leave out (section 07). Second, a search finds similarity, not proof. Whether a hit is an inserted SINE with its own unique flanks, a piece of a duplicated region, or a unit of a satellite array is decided later, from alignments (sections 04 and 05).

# one consensus per query file; work in the directory where the windows may be written
sear dip.fa genome.fa                    # defaults: Slf 0.8, identity 65 %, flanks 50 bp
sear -k dip.fa genome.fa 0.8 65 50       # the same rules written out, keeping the window files for the next query (SINEderella's call)
sear --slop 50,70 dip.fa genome.fa       # 50 bp left flank, 70 bp right flank
sear -b 100 dip.fa genome.fa             # also align the 100 best hits with MAFFT
sear -m dip.fa genome.fa                 # minus-bank rounds: search what is left after cutting out the hits

# outputs: gen-dip.bed (chrom, start, end, identity %, length, strand, bit score) and gen-dip.bnk (FASTA with flanks)
wc -l gen-dip.bed                        # number of loci found for this consensus
  • One consensus per file. The script measures the query length by reading the whole query file; with two sequences in it the length rule goes wrong. Split a bank first (SINEderella does this itself).
  • One genome per directory. The window files are reused when they already exist in the working directory, whatever genome they came from.
  • Underscores in sequence names are handled: the script works on a copy with _ replaced and restores the names in the output.
  • -s N stops once N hits have been found. Useful for a quick look; the result is then not the whole genome.
