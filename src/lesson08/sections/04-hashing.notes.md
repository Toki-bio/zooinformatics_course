# Section 04 Hashing: sources and checks (written 2026-11-05)

## Sources, with the supporting text

**Knuth, D. E. (1963, typeset 1997). Notes on "Open" Addressing.** Sections 1, 5 (Theorem 2) and 6-8 read.
https://jeffe.cs.illinois.edu/teaching/datastructures/2011/notes/knuth-OALP.pdf
- Model: "we consider all of the N^k possible sequences a1, a2, ..., ak to be equally probable" (uniform home slots).
- Section 8: M(N,k) ≈ ½(1 + 1/(1−α)²), T(N,k) ≈ ½(1 + 1/(1−α)), α = (k−1)/N.
  "The estimates for M(N,k) and T(N,k) are upper bounds"; "As α approaches 1, these estimates become less and less accurate."
- Section 7: "the number of comparisons needed to find a given item is the same as the number of comparisons which were needed to enter it in the first place."
- Theorem 2: M(N,k) = ½(1 + E1(N,k)); used for the "exact" curve. The code reproduces his table for N = 5 (1, 6/5, 38/25, 257/125, 3).

**Mohamadi H, Chu J, Vandervalk BP, Birol I (2016). ntHash: recursive nucleotide hashing. Bioinformatics 32(22):3492-3494.** Full text read (PMC5181554), https://doi.org/10.1093/bioinformatics/btw397
- "ntHash uses barrel shifts instead of multiplications"; seed table: "the letters of the DNA alphabet ... are assigned different random 64-bit integers."
- "we can easily compute the hash value for the reverse-complement (as well as the canonical form) of a sequence efficiently, without actually reverse-complementing the input sequence"
- "each extra hash value is computed by few more multiplication, shifting and XOR operations on the initial hash value"
- "a typical use case of computing multiple hash values for 50-mers in DNA sequences of length 250 bp, and shows that ntHash is over 20× faster than the closest competitor"

**ntHash source, version 2.4.0** (meson.build; commit c26bd45, 2026-04-01), https://github.com/BirolLab/ntHash (cloned from github.com/bcgsc/ntHash)
- src/kmer.cpp next_forward_hash: `h_val = srol(fh_val); h_val ^= SEED_TAB[char_in]; h_val ^= srol_table(char_out, k);`
  srol is a split rotation (33-bit and 31-bit sub-words); the page says "rotate" for simplicity.
- src/internal.hpp: `canonical(fwd, rev) { return fwd + rev; }` (the page says "adds the two", for this version).
- src/kmer.cpp is_invalid_kmer: "true if any of the first k characters is not an ACGTU"; NtHash::init skips past such positions.
- "k is not limited to 32" is our reading of the code: hash values are uint64_t and k is an unsigned parameter.

**Marçais G, Kingsford C (2011). A fast, lock-free approach for efficient parallel counting of occurrences of k-mers. Bioinformatics 27(6):764-770.** Read through a web extract of the full text (PMC3051319), https://doi.org/10.1093/bioinformatics/btr011
- "we implement a lock-free hash table with open addressing"
- "we use a quadratic reprobing function: reprobe(i) = i(i + 1)/2"
- "in the event that the hash table is full, it will be written to disk instead of doubling its size in memory"

**Bloom BH (1970). Space/time trade-offs in hash coding with allowable errors. CACM 13(7):422-426.** Full PDF opened; abstract and the description of the bit-setting method read, not the whole analysis. https://doi.org/10.1145/362686.362692 (copy: https://www.cs.princeton.edu/courses/archive/spr05/cos598E/bib/p422-bloom.pdf)
- "The computational factors considered are the size of the hash area (space), the time required to identify a message as a nonmember of the given set (reject time), and an allowable error frequency."
- "exploiting the possibility that a small fraction of errors of commission may be tolerable"

**Putze F, Sanders P, Singler J (2007). Cache-, Hash- and Space-Efficient Bloom Filters. WEA 2007, LNCS 4525.** Conference version: section 3 and the experimental results read, not every section; archived copy: https://web.archive.org/web/2015/http://algo2.iti.kit.edu/singler/publications/cacheefficientbloomfilters-wea2007.pdf
- "Standard Bloom filters are cache-inefficient since k cache misses are generated by every input operation and (false or true) positive membership query."
- "For negative queries, only less than two cache misses are generated, on the average. This is because each bit is set with probability q = 1/2, when choosing the optimal k"
- "It consists of a sequence of b comparatively small standard Bloom filters (Bloom filter blocks), each of which fits into one cache-line. Nowadays, a common cache line size is 64 bytes = 512 bits."
- "the first hash value selects the Bloom filter block to be used. Additional hash values are then used to set or test bits as usual, but only inside this one block. A blocked Bloom filter therefore only needs one cache miss for every operation."
- "using the typical value c = 8 bits per element ... the FPR is 0.0231 instead of 0.0215 for B = 512 bits. By increasing c by one, we can (over-)compensate for that."
- "for c = 20 and k = 14, the FPR almost triples: it rises from 0.0000671 to 0.000194"
- "For both positive queries and insertions, the blocked Bloom Filter variants outperform the original Bloom filter ... The maximum speedup factor is close to 4, using 32% more memory than the standard variant."

**Wikipedia, "Hash table" and "Linear probing"** (read through a web extract 2026-11-05), used only for the general comparison in the chaining table.
https://en.wikipedia.org/wiki/Hash_table , https://en.wikipedia.org/wiki/Linear_probing
- "an open-addressed hash table cannot have a load factor greater than 1"
- chaining tables "suffer gradually declining performance as the load factor grows, unlike the sharply decreasing performance of open addressing hash tables around α = 1"
- "Linked lists in separate chaining may not be cache-conscious"; "linear probing could lead to better utilization of CPU cache"
- "Primary clustering also affects unsuccessful searches, since like insertions, they must travel to the end of a run."

## Our own reasoning (no outside source needed; checked in code)
2-bit values (GATTA 572, TAATC 781, ATTAC 241, GTAAT 707); complement = 3 − code; numeric order = alphabetical order (all 1,024 5-mers);
4^12 and 4^31; last 6 bits = last three bases; the rolling updates; "doubling the slots" (α 0.45 gives 2.15 probes); a Bloom filter plus exact table gives exact answers.
The toy's hash is an arbitrary multiply-and-shift mixer, not taken from any tool.

## Controls run
- Node, on the code taken from the .js file: 1,400 table states (200 random reads, load 9 to 63) × 1,024 5-mers: table lookup equals the plain list in every case.
- Negative controls: a lookup without probing (998/1024 agree) and a lookup on the wrong strand (944/1024) are both detected.
- 3,000 simulated fills: mean probes match Knuth's exact curve (α 0.5: 2.38 vs 2.35; 0.75: 6.05 vs 6.13; 0.875: 13.25 vs 13.13; 0.969: 28.72 vs 28.08). The large-table estimate is far above at high load (0.875: 32.5), as Knuth says it should be.
- Browser, at widths 1100 and 420: all buttons clicked; the on-page control read 1,024 of 1,024 for an empty table, 21 insert steps, a full table and 12 new reads; a k-mer and its reverse complement give the same slot; bad input gives a message.
