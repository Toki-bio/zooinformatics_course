02Line tools: grep to agrep

The oldest way to search a sequence file is the same tool you use on any text: grep. It is fast, it is already installed, and for a short exact motif it is often all you need. But grep was built for text, and a sequence file is not text in the way it expects. This section shows the tools in the grep family, what each one adds, and the five ways they quietly give a wrong answer on FASTA.

Every row except seqkit grep works on lines. The GNU manual says it directly: since newline also separates patterns, "there is no way to match newline characters in a text". Everything that goes wrong below follows from that.

Explain

What does a line-based search miss?

A toy 121-bp sequence is printed in lines of the width you choose, like a FASTA file. Type a pattern (letters A, C, G, T, N). Three counts follow. Line search is what grep -o on the wrapped file finds. Unwrapped, one strand searches the joined sequence for the pattern as typed. Both strands adds the reverse complement of the pattern. Matches in green are found by the line search; orange matches are cut by a line break; red matches are on the other strand.

Trap 1: wrapped lines

FASTA files are usually wrapped at 60 or 80 letters per line, so a motif that crosses a line end is split in two and no line contains all of it. A toy file, with the pattern GGCTTAACCGATTAC crossing the end of the first line of seq1 (the file is shown first):

>seq1 toy
ACGTTGCAAGGCTTAAC
CGATTACAGGGATCCTA
GGCATTTACGCGAATTC
>seq2 toy
TTGAGCTCCCTGTAATC
GAGTTCCTAGCATGCAA
$ grep -c GGCTTAACCGATTAC toy.fa
0
$ awk '/^>/{if(s)print s;print;s="";next}{s=s $0}END{print s}' toy.fa > flat.fa
$ grep -c GGCTTAACCGATTAC flat.fa
1

The awk line joins the sequence lines of each record into one line. It is the cheap fix. Join per record, as the awk does: removing every newline from the whole file would glue the end of one record to the start of the next and could create matches that exist in no sequence. seqkit grep -s avoids the problem because it reads records, not lines.

Trap 2: the other strand

DNA is double-stranded and a copy of a motif can sit on either strand. grep looks for the text you typed. The reverse complement is the pattern read backwards with A and T swapped and C and G swapped; here it is GTAATCGGTTAAGCC, and you have to search for it separately:

$ echo GGCTTAACCGATTAC | awk '{o="";for(i=length;i>0;i--)o=o substr($0,i,1);print o}' | tr ACGT TGCA
GTAATCGGTTAAGCC
$ grep -c GTAATCGGTTAAGCC flat.fa     # the toy file has no copy on this strand
0

seqkit grep -s -p PATTERN does this for you: its help says that when searching by sequence "both positive and negative strands are searched" and that -P restricts it to the positive strand. This was read from the seqkit 2.14.0 help and source. seqkit is not installed on the machine where we ran the other commands, so its commands on this page were not run.

Trap 3: compressed files

Sequencing data usually comes as .fastq.gz. The letters in a gzip file are not the letters of the sequence, so grep on it finds nothing. Decompress into a pipe:

$ grep -c TAAC toy.fa.gz
0
$ gzip -dc toy.fa.gz | grep -c TAAC
1
$ rg -c TAAC toy.fa.gz       # no -z: nothing is printed, exit status 1
$ rg -z -c TAAC toy.fa.gz
1

A zero without an error message is the dangerous part: it looks like "the motif is not in the data".

Trap 4: one pattern or many

-f FILE reads one pattern per line and prints lines that match any of them. Add -F when the patterns are plain letters, so they are not read as regular expressions:

$ printf 'TAAC\nGGGATCC\n' > pats.txt
$ grep -F -f pats.txt toy.fa
ACGTTGCAAGGCTTAAC
CGATTACAGGGATCCTA
$ printf 'TAAC\n\n' > p2.txt      # a blank line sneaked in
$ grep -c -F -f p2.txt toy.fa
7

The last result is every line of the file (7), because a blank line is an empty pattern and the empty pattern matches everywhere. The GNU manual says "the empty regular expression matches the empty string"; a stray blank line in a pattern file is a common cause of "everything matched". The output also does not say which pattern matched a line.

Trap 5: counting versus extracting, and the locale

-c counts lines, not matches; ripgrep's guide says the same ("a count of total matched lines"). -o prints each match on its own line, so counting those counts matches:

$ printf 'AAAAAA\n' | grep -c AA
1
$ printf 'AAAAAA\n' | grep -o AA | wc -l
3

-o finds matches that do not overlap, so AAAAAA holds 3 hits of AA, not 5.

The locale is the setting that tells programs which alphabet and sort order to use (LANG, LC_ALL). The GNU manual says it changes how character classes and bracket expressions are read, and that the traditional reading is obtained with LC_ALL=C. You will often read that LC_ALL=C grep is also much faster; the manual does not say this. We timed one pattern in a 122 MB text file of 2 million random 60-letter lines with LC_ALL set to C, en_US.UTF-8 and C.UTF-8: all three took about 0.44 s. That machine has no en_US locale installed, so the test tells us nothing about a typical Linux server. The speed gain from LC_ALL=C is not verified here. One more locale effect we did see: grep -P refused to run under LC_ALL=C on that machine ("supports only unibyte and UTF-8 locales"), so we ran it with C.utf8.

Regular expressions and multi-line search

With -E or -P you can write GG[CT]TT for "GG, C or T, then TT", or A{2}C. Neither is an alignment: the pattern stays exact except where you spell out the choices. Ripgrep can match across line ends if you ask: -U ("permit matches to span multiple lines") lets you write the line break into the pattern:

$ rg -U 'GGCTTAAC\nCGATTAC' toy.fa
ACGTTGCAAGGCTTAAC
CGATTACAGGGATCCTA
$ rg -c -U 'GGCTTAAC\nCGATTAC' toy.fa
1

This only works if you know where the line break falls, which depends on the wrapping width of the file, so it is not a general fix for Trap 1.

Allowing errors: agrep and seqkit

Real copies differ from the pattern. agrep from the TRE library "prints lines approximately matching a pattern". Its manual gives the example agrep -2 optimize foo.txt, which "outputs all lines in file foo.txt that match 'optimize' within two errors". Options -D, -I and -S set the cost of a deletion, an insertion and a substitution, and -B prints only the best-matching records. Like grep it works on records, which by default are lines (-d changes the record delimiter), so the wrapped-line trap applies in full. agrep was not run: it is not installed here, and we read its manual page only.

seqkit grep -s -p PATTERN -m 2 allows up to 2 mismatches. Its help says "Only substitutions are allowed; insertions and deletions are not", and that a single pattern of up to 64 characters with 1 to 4 mismatches uses an optimized search. The help also warns that for large genomes "using mapping/alignment tools would be faster". That points ahead: the later sections of this lesson are about those tools.

These tools scan every letter of the file again for each search. For one short motif in a few files that is fine. For millions of patterns, a pattern with gaps, or a genome you will search many times, continue with sections 03 and 08.

Simple explanation with examples: why "grep says zero" is not the same as "it is not there"

Think of a file as a long strip of paper cut into rows of equal length and stacked. grep reads one row at a time. If your word starts at the end of one row and finishes on the next, no single row contains it. Joining the rows into one strip fixes that. Searching only for the word as written misses the copy printed on the back of the strip, which is the other strand. And a compressed file is the strip put through a shredder: the letters you search for are not in it until you unpack it.

So after a zero from a line tool, ask three questions: is the file wrapped, did I search both strands, and was the file compressed?
