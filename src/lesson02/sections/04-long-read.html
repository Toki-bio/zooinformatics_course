04Assembling long reads

A long read is thousands to hundreds of thousands of bases long. One read can run straight through a repeat that would cut a short-read assembly into pieces. This section shows why that works, how long-read assemblers are built, which assembler to choose for which reads, and what files come out.

Why read length beats repeats

An assembler joins reads by finding where they overlap (the end of one read matches the start of another). Inside a repeat this fails: a read that lies entirely within a copy of the repeat matches every copy equally well, so the assembler cannot tell which copy it came from. The assembly breaks there, and all copies are usually collapsed into one.

The fix is a read that bridges the copy: it starts in unique sequence on one side, runs through the whole repeat, and ends in unique sequence on the other side. Then there is no doubt where that copy belongs. So the rule of thumb is simple: a repeat copy is resolved only if some reads are longer than the repeat plus a safe overlap on each side. With short reads the same rule applies to k-mers (the k − 1 rule in section 03).

Simple explanation with examples: overlaps, layout, consensus

Most long-read assemblers follow three steps, called overlap–layout–consensus (OLC). Take three short "reads" from the sentence THE_CAT_SAT_ON_THE_MAT:

read 1: THE_CAT_SAT read 2: T_SAT_ON_TH read 3: ON_THE_MAT overlap 1→2: "T_SAT" 2→3: "ON_TH" layout 1 → 2 → 3 consensus THE_CAT_SAT_ON_THE_MAT
  1. Overlap
    Find every pair of reads whose ends match. Comparing every read with every other in full would take forever, so tools first compare short sampled k-mers called minimizers, and only then check the candidates.
  2. Layout
    Put the overlaps into a graph: each read is a node, each overlap an arrow. If read 1 overlaps 2, 2 overlaps 3, and 1 also overlaps 3, the arrow 1→3 adds nothing and is removed (transitive reduction). What remains is a string graph. A stretch of the graph without branches becomes a unitig; contigs are built from unitigs.
  3. Consensus
    Line up all reads along the path and take the majority base at each position. Errors in single reads are outvoted.

A repeat shows up as a branch: the path enters the repeat from two places and leaves to two places, and only a read that bridges the repeat says which exit belongs to which entrance. That is exactly the slider box above.

Read types and why accuracy matters

Long reads differ in two things: how long they are and how many errors they carry. Accuracy is written as a Q value: Q20 means 1 error in 100 bases, Q30 one in 1,000.

Why accuracy decides haplotypes. A diploid animal carries two copies of each chromosome, which differ at heterozygous sites, for example one site in 200 at 0.5 % heterozygosity. When an assembler compares two reads, it sees two kinds of difference: real ones (the reads come from different parents' copies) and sequencing errors. If errors are much rarer than real differences, reads can be sorted into two haplotypes. If errors are as common as real differences, they cannot, and the two copies get merged or tangled.

This toy compares one pair of reads. Real assemblers (for example hifiasm's error correction) look at many reads at once and keep only differences that several reads agree on, which separates haplotypes at higher error rates than this toy suggests. The direction is the same: fewer errors, longer overlaps and higher heterozygosity all make separation easier. Species A's heterozygosity was moderate, well below 1 %.

Read correction lowers the error rate before assembly. It aligns each read against the other reads from the same region and fixes positions where the read disagrees with the rest. The danger is that a correction step that ignores haplotypes "fixes" real heterozygous sites too. The current tools are therefore haplotype-aware: they keep a difference when several reads share it.

  • hifiasm corrects reads itself, in 3 rounds by default (-r 3), and with --ont also uses the base quality values, so it needs FASTQ input.
  • Dorado correct (ONT's tool; it runs the HERRO model) is for R10.4.1 reads with an average length of at least 10 kb and preferably ≥30× coverage. ONT recommends a machine with >64 CPU cores, >256 GB RAM and a GPU with >32 GB memory. The output is FASTA (quality values are lost), used for example as the accurate reads in Verkko.
  • NextDenovo corrects the longest reads (its "seeds") with its own module NextCorrect, then assembles them.

Why not use an exact k-mer method, as for short reads? At 3 % errors only (0.97)30 ≈ 40 % of 30-mers in a read are error-free (Shasta's documentation makes this point), so most k-mers are wrong. Long-read tools therefore use approximate matches, short k-mers, or correct the reads first.

The assemblers

Each tool builds a slightly different graph. You do not need the details to run them, but the graph type explains what each one is good at.

hifiasm
Corrects reads with haplotype awareness, then builds a string graph in which the two haplotypes stay separate as "bubbles" (two parallel paths). From this graph it writes a primary assembly and two partly phased haplotype assemblies. It removes duplicated haplotype copies itself (-l, purge level), so a separate purge_dups run is usually not needed (section 06). Designed for HiFi; since version 0.21 it also takes ONT simplex R10 reads with --ont (marked "beta" in its help text; hifiasm 0.25.0 is the current release). Can add ultra-long reads (--ul), Hi-C or parental reads for full phasing.
Flye
First joins reads greedily into rough long sequences (disjointigs), then builds a repeat graph from them using approximate matches, which tolerate read errors. Every repeat longer than the minimum overlap is collapsed into one edge of the graph; Flye then uses reads that bridge a repeat to untangle it. Produces one collapsed (haploid) assembly: where the two parental copies differ, it picks one, and may report very different stretches as alternative contigs. Works with noisy and accurate reads alike. Current version 2.9.6 (May 2025).
Verkko
A pipeline for telomere-to-telomere (T2T) assembly. It builds a graph from accurate reads (HiFi, ONT duplex, or HERRO/hifiasm-corrected simplex), then threads ONT ultra-long reads through it to resolve long repeats. Phases with parental (trio) or Hi-C data. Needs Snakemake and several helper programs; easiest via conda.
NextDenovo
"Correct then assemble" with a string graph, for noisy ONT or PacBio CLR reads. Its documentation says it is optimised for seed reads (the longest 30–45× of data) of at least 10 kb; with shorter reads it "may produce unexpected results". Version 2.5.2.
Shasta
Assembler optimised for ONT reads. Stores reads in run-length encoding and finds overlaps through short marker k-mers. Needs uncompressed input and a ready-made --config matching the reads (there are R10.4.1 raw and HERRO configurations). Version 0.14.0.
Raven
OLC assembler for uncorrected long reads, with built-in Racon polishing. Small and quick; last code change in 2023.
wtdbg2
Cuts reads into 1,024-bp pieces and merges similar pieces into a fuzzy Bruijn graph. Very fast, but last updated in 2020, and its README warns that ONT assemblies may come out smaller than the true genome.
Canu
The classic correct-trim-assemble pipeline (and HiCanu for HiFi). Its README now says Canu has reached end of life and recommends Flye, hifiasm or Verkko instead.

Running them

The main options are explained below the commands. 2> file.log saves the progress messages; keep these logs, they contain the coverage and k-mer estimates you will need later.

# ---- hifiasm (0.25.0) ----
# HiFi reads, heterozygous animal (default: purge level 3, writes primary + hap1 + hap2)
hifiasm -o sp.asm -t 32 hifi.fq.gz 2> sp.asm.log
# ONT R10 simplex reads (FASTQ required: base qualities are used)
hifiasm -o sp.ont -t 64 --ont -f38 --telo-m CCCTAA ont.fq.gz 2> sp.ont.log
# primary + alternate instead of hap1/hap2; -l0 for inbred or homozygous animals
hifiasm -o sp.asm -t 32 --primary hifi.fq.gz 2> sp.pri.log
# HiFi + ultra-long ONT + Hi-C: the full combination
hifiasm -o sp.asm -t 32 --ul ul.fq.gz --h1 hic_R1.fq.gz --h2 hic_R2.fq.gz hifi.fq.gz 2> sp.hic.log

# ---- Flye (2.9.6) ----
flye --nano-hq ont.fq.gz --out-dir flye_ont --threads 32       # R10 / Q20-class nanopore
flye --nano-raw ont.fq.gz --out-dir flye_raw --threads 32      # older, noisier nanopore
flye --pacbio-hifi hifi.fq.gz --out-dir flye_hifi --threads 32
# less RAM: first stage uses only the longest 40x of reads (needs --genome-size)
flye --nano-hq ont.fq.gz -g 2.7g --asm-coverage 40 -o flye_ont -t 32
flye --nano-hq ont.fq.gz -o flye_ont -t 32 --resume            # continue after a crash

# ---- ONT read correction, then Verkko ----
dorado correct ont.fq.gz --to-paf > overlaps.paf               # CPU part: all-vs-all overlaps
dorado correct ont.fq.gz --from-paf overlaps.paf > corrected.fasta   # GPU part (input .gz must be bgzip, not plain gzip)
verkko -d verkko_asm --hifi corrected.fasta --nano ul.fq.gz

# ---- NextDenovo (2.5.2): settings in a config file ----
ls ont.fq.gz > input.fofn   # fofn = "file of file names": one read file per line
cp NextDenovo/doc/run.cfg .    # edit: read_type = ont, genome_size = 2.7g, job_type = local
nextDenovo run.cfg             # result: 01_rundir/03.ctg_graph/nd.asm.fasta

# ---- Shasta (0.14.0): uncompressed input, configuration by read type ----
shasta --input ont.fasta --config Nanopore-r10.4.1_e8.2-400bps_sup-Raw-Jan2025 --threads 32
-o / --out-dir
hifiasm: the prefix of every output file. Flye: a folder.
-t / --threads
CPU threads. Both tools default to 1, so always set it. On a shared server use half the cores or fewer (see section 02).
-f38 (hifiasm)
Size of the Bloom filter used while counting k-mers: it takes 2(f−3) bytes, so the default -f37 = 16 GB and -f38 = 32 GB. The manual recommends 37 for human, 38–39 for genomes much larger than human, and -f0 for small genomes.
-l (hifiasm)
Purge level for duplicated haplotype copies: 0 = off (use for inbred or homozygous samples), 1 = light, 2/3 = aggressive. Default 3 (0 in trio mode). The README warns that purging "may introduce misassemblies".
--primary (hifiasm)
Write a primary and an alternate assembly (p_ctg + a_ctg) instead of hap1 + hap2. -l0 does the same. See section 07.
--telo-m (hifiasm)
Telomere motif, written as the 5′-end repeat. Vertebrates, including mammals, use CCCTAA (the reverse complement of TTAGGG); other groups can differ, so look up yours. Helps keep telomeres at contig ends.
--hg-size / --hom-cov (hifiasm)
Haploid genome size, or the homozygous coverage, if hifiasm misjudges coverage from its k-mer plot. The log line homozygous read coverage threshold tells you what it chose; if that is not near your real coverage, the assembly may be too large or too small.
--nano-hq vs --nano-raw (Flye)
Read type sets Flye's internal error model. Flye's table: --nano-hq for "Guppy5+ SUP or Q20 (<5 % error)", with R10 (<3 %) as its default since 2.9.6; --nano-raw for older data with 10–15 % (up to 20 %) errors. Pick by the error rate you measured in lesson 1, not by the instrument name.
-g / --genome-size (Flye)
Optional since Flye 2.8; needed only with --asm-coverage, and otherwise only used for coverage estimates.
--min-overlap (Flye)
Chosen automatically from the read length distribution (reads N90), typically 3–10 kb and down to 1 kb for short reads. Flye expects >10× coverage and read N90 over 1 kb (5 kb+ recommended); it will not work with reads shorter than 1 kb.

How long and how much memory

Numbers from the tools' own documentation (single machine):

  • hifiasm, mouse 2.6 Gb, HiFi 25×: 4.8 h with 48 threads, 76 GB RAM (an old version, 0.12). Human HiFi 32–36×: about 7–8 h, 114–137 GB.
  • Flye, human: ~450 GB RAM for ONT and ~140 GB for HiFi (FAQ); human ONT 35× took 3,100 CPU hours. Memory grows with genome size × coverage; --asm-coverage 40 lowers it.
  • wtdbg2, human ONT 36×: 31 h, 222 GB. Dorado correct: GPU needed (see above).

hifiasm saves its corrected reads and overlaps as *.bin files. A second run with the same -o prefix reuses them and finishes much faster (for example to switch to --primary). Delete the bins, or use -i, if you changed the reads or upgraded hifiasm.

What comes out

Both main tools write the assembly as a GFA file (Graphical Fragment Assembly): a text file in which lines starting with S hold the sequences (segments) and lines starting with L the links between them. Flye also writes FASTA; for hifiasm you convert.

The last letter of a hifiasm contig name says whether it is linear (l) or circular (c). In an animal genome the mitochondrion is the circular molecule to expect, but it does not always come out as one circular contig (see the species A box below and section 11).

# GFA → FASTA: print every S line as a FASTA record (hifiasm FAQ)
awk '/^S/{print ">"$2; print $3}' sp.asm.bp.p_ctg.gfa > sp.asm.p_ctg.fa
# the same with gfatools, wrapped at 60 bases per line
gfatools gfa2fa -l 60 sp.asm.bp.p_ctg.gfa > sp.asm.p_ctg.fa

# ALWAYS check which assembly a FASTA really is, by its headers
grep -m 3 '>' sp.asm.p_ctg.fa            # ptg… = primary; h1tg… / h2tg… = haplotype 1 / 2
# and name input files explicitly in scripts, never with a wildcard:
# ls sp.asm*.p_ctg.gfa lists bp.hap1… BEFORE bp.p_ctg…

In our projects: the wildcard that picked the wrong assembly (species A)

We assembled species A, an unpublished rodent genome (long reads only, roughly 40×, read N50 above 10 kb), with hifiasm 0.25.0 --ont --telo-m CCCTAA -f38 on 64 threads. A follow-up script picked "the first *.p_ctg.gfa" with a wildcard. Alphabetically bp.hap1.p_ctg.gfa comes before bp.p_ctg.gfa, so every "hifiasm" number first sent to collaborators (BUSCO and N50, both lower than the primary's) was haplotype 1. The FASTA called …p_ctg.fa had the same size as hap1 and headers h1tg…. When the real primary was finally evaluated, it was the best assembly we had:

Three lessons. Check headers before you report numbers. The haplotype sets of a hifiasm run without Hi-C or parental data are only partly phased and need not be complete: hap1 lost BUSCO genes as missing, not fragmented. And hifiasm --ont gave nearly ten times the N50 of Flye even though only about a fifth of the reads were above Q20. These reads were probably CycloneSEQ rather than ONT (the read IDs match a CycloneSEQ run report; not confirmed by the provider), so a nanopore mode worked on them, but the ONT-specific polishing models are questionable (section 06).

One more thing to expect: the mitochondrial genome came out as one contig made of several tandem copies of the circle, a known artefact of assembling a circular molecule (section 11).

In our projects: short reads and low coverage (species B and C)

For species B and C, two unpublished small-mammal genomes, we had CycloneSEQ reads (first labelled "ONT" in our notes, corrected later), assembled with Flye 2.9.5 --nano-raw --genome-size 2g on 16 threads (about a day for B), then Medaka, NextPolish and purge_dups.

C had longer reads but only about 10× (Flye's own log said a little less); Flye's FAQ says coverage below 10× is not recommended, and C came out with less than half the N50 and about 10 points less BUSCO. An early report quoted higher long-read coverages for both; those numbers had no source and were wrong. B, with roughly 25× but a read N50 under 3 kb, still reached only a few hundred kb, against more than 10 Mb for species A with reads about four times longer: read length limits contiguity, as in the slider box above.

Two choices we would now make differently. By Flye's own read-type table, reads with ≈2–3 % errors belong in --nano-hq, not --nano-raw (we have not tested whether it changes the result). And the 2 Gb genome size was a guess; the assemblies came out about a fifth larger.

Common pitfalls

  • Wrong read type. Check the platform from the read headers and the error rate from lesson 1 before choosing a mode or a polishing model.
  • Mixing up assembly files. Name files explicitly, check contig names, and write next to every number which file it came from.
  • Expecting two haplotypes from Flye. Flye gives one collapsed set. hifiasm hap1/hap2 without Hi-C or parental reads are partly phased (section 07).
  • Too little coverage. Below ~10× contigs fall apart; HiFi needs about 13× per haplotype according to the hifiasm FAQ.
  • Reads too short for the tool. NextDenovo wants ≥10-kb seeds; Dorado correct wants an average of ≥10 kb; Flye drops reads under 1 kb, and hifiasm --ont drops reads under 1 kb and below mean Q10 by default (--rl-cut, --sc-cut).
  • Reusing old hifiasm *.bin files after changing reads or version: the release notes recommend rerunning ONT assemblies from scratch.
