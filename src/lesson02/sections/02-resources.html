02System requirements: RAM, CPU, disk and time

An assembler that runs out of memory after two days has cost two days. Before you start one, estimate how much memory, how many processor cores, how much disk space and how much time it will need, and check that the machine has them free at the moment.

Why this comes first: a run that died

The short reads of species D (one of our unpublished small-mammal genomes) went into SPAdes with a 256 GB memory limit (-m 256), 16 threads and three small k values. Even after the reads had been downsampled, the run stopped in its first step, read error correction, with "OS return value: 12". Code 12 is the Linux "out of memory" error. No assembly came out of that run.

The five resources

RAM (memory)
The working memory the program keeps its data in while it runs. Assemblers hold large tables (of k-mers, overlaps or graphs) in RAM. If a program asks for more RAM than is free, Linux either kills it (the OOM killer) or starts moving memory to disk (swap), which makes everything on the machine crawl. RAM is the resource most often in short supply.
Cores and threads
A core is one processing unit of the CPU. A thread is one stream of work a program runs; with -t 16 it runs up to 16 at once, ideally one per core. A CPU-hour (core-hour) is one core busy for one hour: 16 threads for 10 hours use up to 160 CPU-hours.
Disk
Space for the input reads, for the intermediate files written during the run, and for the results. The peak during the run is often many times larger than the final assembly.
Wall time
The time on the clock from start to finish (as on a wall clock). It is CPU-hours divided by the threads that are actually busy, plus waiting for the disk.
GPU
A graphics processor. Most assemblers do not use one. Neural-network tools do: dorado (basecalling, read correction, polishing) and, optionally, Medaka. A GPU has its own memory (VRAM), and that sets how large a batch it can process.

Why memory grows with genome size, coverage, errors and heterozygosity

Most assemblers start by counting or indexing k-mers (lesson 1). Memory follows the number of different k-mers they must keep, not the genome size alone. A clean haploid genome gives about one different k-mer per base. Each difference between the two parental copies (a heterozygous site) adds up to k new k-mers. Each sequencing error also adds up to k new k-mers, and these are almost all seen only once. The number of error k-mers grows with the amount of reads, so coverage and error rate multiply each other.

With noisy long reads the error k-mers outnumber the genome's own k-mers many times over. Assemblers deal with this in different ways. Flye counts k-mers first and keeps only the "solid" ones, those seen often enough to be unlikely errors. hifiasm puts a Bloom filter in front of its k-mer counter, so k-mers seen only once are dropped before they take space. ABySS 2 holds its whole k-mer table in Bloom filters. These are simplified counts: repeats lower the genome bar, and an error near a read's end touches fewer than k k-mers.

Simple explanation with examples: why one error costs up to k k-mers

Take k = 5 and a read with one wrong base (red). Every 5-letter window that covers the wrong base is a k-mer the genome does not have:

genome ACGTTGCAAC read ACGTAGCAAC windows ACGTA CGTAG GTAGC TAGCA AGCAA → 5 false k-mers from 1 error

A 2.5 Gb genome read to 25× with 3 % errors has 62.5 billion read bases and about 2 billion errors. Each error gives up to 21 false 21-mers: tens of billions of false k-mers against 2.5 billion real ones. With HiFi reads (0.1 % errors) the false k-mers drop below the number of real ones, and most of them are seen only once, so a filter removes them.

A heterozygous site works the same way, but the "error" is real: the second parental copy gives up to k k-mers of its own, each seen at about half the coverage.

Overlap-based long-read assemblers (Canu, NextDenovo, hifiasm, Flye in its later steps; all described in section 04) also store which reads overlap which. That table grows with the number of reads and with repeats. The tools' own documentation therefore states memory per amount of input:

  • Flye: "Memory consumption grows linearly with genome size and reads coverage". Human assemblies take about 450 GB of RAM with ONT reads and about 140 GB with HiFi reads; memory is lower for more accurate reads.
  • Shasta: about 4 to 6 bytes of RAM per input base, around 1 TB for a human genome at 60×.
  • NextDenovo: each read-correction job needs about (total input bases ÷ 4) bytes; each alignment job 32 to 64 GB.
  • hifiasm: the published table gives 68 to 137 GB for 2.2 to 3.1 Gb genomes at 22 to 36× HiFi, and 463 GB for a 9.5 Gb frog genome.
  • ABySS 2: the Bloom filter budget B follows genome size: B=50G for human (3.1 Gb), B=2G for Caenorhabditis elegans (~101 Mb).

Why disk use explodes

Count three things separately: the inputs, the peak of intermediate files, and what you keep.

  1. Inputs
    Compressed FASTQ in our projects took about 0.53 bytes per base for Illumina NovaSeq reads and about 0.87 bytes per base for the long reads (two long-read data sets, both close to that value). Uncompressed FASTQ takes a little over 2 bytes per base, one for the letter and one for its quality. Many tools decompress to a temporary file or a database first.
  2. Intermediates
    Canu's FAQ: a human genome at 40 to 50× PacBio or Nanopore "typically requires 1-2TB of space at the peak"; plan for 3 TB (200 GB for HiFi). MaSuRCA lists 5 TB of disk for a mammal. SPAdes checkpoints (--checkpoints all) "may take ... a significant amount of disk space". Every polishing round writes a BAM of all reads; samtools sort writes temporary files next to it unless you point -T elsewhere. hifiasm saves its corrected reads and overlaps as *.bin files so a rerun can skip that work.
  3. Outputs
    A FASTA file takes about 1 byte per base: a hifiasm primary assembly of about 3 Gb is a .gfa file of about 3 GB (GFA, hifiasm's output format). A haplotype-resolved run writes two or three assemblies of that size. Keep the logs; they are tiny and they record what was run.
  4. Reference databases
    The FCS-GX contamination database needs 470 GiB of disk (section 09); BUSCO lineage sets are downloaded into busco_downloads/ in the current folder unless you give --download_path.

Measure instead of guessing. When the docs give no number (for example the size of a BAM), run the step on a 1 % random subsample of the reads (seqkit sample -p 0.01), look at the file sizes with du -sh, and multiply by 100. For memory and time, wrap the command in /usr/bin/time -v: its line "Maximum resident set size" is the peak RAM in kilobytes. Memory and time of assemblers do not scale exactly linearly, so treat a subsample run as a lower bound.

Threads and wall time

Doubling the threads does not halve the wall time. Every program has steps that run on one thread (reading input, writing output, some graph steps), and threads wait for the disk and for each other. The share of the work that can run in parallel sets the limit. This is known as Amdahl's law.

Try it

More threads, less benefit

A toy job that takes 100 hours on one thread. Set what share of it can run in parallel and how many threads you give it.

Real numbers. hifiasm's README lists CPU time and wall time at 48 threads. For human HG002 it is 305.4 CPU-hours and 7.7 hours of wall time: 305.4 ÷ 7.7 ≈ 40 threads busy on average out of 48. For mouse, 172.9 ÷ 4.8 ≈ 36 of 48. At the other extreme, Medaka on our species B used about 2 cores' worth of CPU (~200 %) even with 16 threads: its slow step is neural-network inference, and its README suggests splitting that step by contig into separate jobs (medaka inference --regions) instead of adding threads.

Running on a shared server without hurting anyone

  1. Look before you start
    nproc (threads), free -g (RAM; read the "available" column), df -h (free disk on each filesystem), top or htop (who is running what).
  2. Write big files to the scratch disk, never to /home
    Scratch filesystems are large; /home is usually small and shared by every account. A full /home stops everyone's conda, pip and login scripts. Start each job with cd /scratch/dir || exit 1 on its own line, so a failed cd stops the job instead of letting it write into the home folder.
  3. Move the caches too
    Package managers (conda, pip) and container tools (Apptainer) write caches into your home folder (~) by default. Point them at scratch with environment variables: TMPDIR, CONDA_PKGS_DIRS, XDG_CACHE_HOME (pip respects it), APPTAINER_CACHEDIR.
  4. Set every limit explicitly
    Some tools take everything by default: MEGAHIT 90 % of RAM and all threads, meryl all RAM and up to 64 CPUs, dorado correct all threads. Others take too little: BUSCO one CPU. Give each its -t/threads= and a memory limit (-m, memory=, B=, -s).
  5. Be polite with nice and ionice
    nice -n 19 gives the job the lowest CPU priority (niceness runs from −20, most favoured, to 19, least). ionice -c 3 puts it in the "idle" disk class: it gets disk time only when no other program has asked for it for a while. Neither limits memory.
  6. Make the run survive a dropped connection, and record what it used
    nohup … & (or a tmux/screen session) keeps the job running after you log out. /usr/bin/time -v -o run.time.txt writes peak memory and wall time to a file. Read the first lines of the log right after starting; an error there means the job is not doing what you think.
  7. Before relaunching a corrected run, stop the old one
    Find its process ID with ps -u $USER -f and stop it by that ID (kill PID), then check it is gone. Never kill by program name: other people may be running the same program.
# 1. what is free right now?
nproc; free -g; df -h /scratch /home

# 2. keep data, temporary files and caches off /home
export TMPDIR=/scratch/$USER/tmp
export CONDA_PKGS_DIRS=/scratch/$USER/conda_pkgs
export XDG_CACHE_HOME=/scratch/$USER/cache
export APPTAINER_CACHEDIR=/scratch/$USER/apptainer
mkdir -p "$TMPDIR" "$CONDA_PKGS_DIRS" "$XDG_CACHE_HOME" "$APPTAINER_CACHEDIR" /scratch/$USER/asm
cd /scratch/$USER/asm || exit 1

# 3. low priority, survives logout, records peak RAM and time
nohup nice -n 19 ionice -c 3 /usr/bin/time -v -o flye.time.txt \
    flye --nano-raw reads.fq.gz --out-dir flye_out --genome-size 2.5g --threads 16 \
    > flye.stdout 2> flye.stderr &
sleep 60; tail flye.stderr flye_out/flye.log   # read the start of the log now

# 4. afterwards: peak memory (kB) and wall time
grep -E 'Maximum resident|Elapsed' flye.time.txt

# explicit limits for tools that otherwise take everything (or too little)
megahit -1 R1.fq.gz -2 R2.fq.gz -o megahit_out -t 16 -m 200e9      # -m in bytes
meryl count k=21 threads=16 memory=64 R1.fq.gz R2.fq.gz output reads.meryl
spades.py --isolate -1 R1.fq.gz -2 R2.fq.gz -o spades_out -t 16 -m 400 --tmp-dir "$TMPDIR"
busco -i asm.fa -m genome -l mammalia_odb10 -c 16 -o busco_asm --download_path /scratch/$USER/busco_downloads

In our projects

  • Machines. DRAGEN: 64 cores, 503 GB RAM. therioserver: 128 cores, ~499 GiB RAM, with a "half cores only" policy (64 threads). Both are a little under the 512 GiB that FCS-GX asks for; I could not find a record of FCS-GX having been run on either.
  • Species B, on DRAGEN at 16 threads with nice -n 19 and ionice -c 3 (a mammal-size genome, CycloneSEQ long reads at roughly 25×): Flye about a day, Medaka about half a day (at ~200 % CPU; time followed the number of contigs more than the amount of reads), NextPolish more than a day (task = best, two iterations of its short-read modules; section 06). Flye's run came to fewer than 10 thread-hours per Gb of reads, well below the scaling in Flye's FAQ; peak memory was not recorded.
  • Species A, on therioserver with 64 threads. hifiasm was run with -f38, a 32 GiB Bloom filter. k-mer counting with jellyfish needed a 40G hash (-s 40G); a 10G hash was too small.
  • Species D. SPAdes ran out of memory under a 256 GB limit during read error correction, after downsampling.
  • Memory requested on the Monsoon cluster for Darevskia mixta (~16× NovaSeq): ABySS 120 GB, MEGAHIT 240 GB, SPAdes 470 GB (a 500 GB node). These are requests, not measured peaks. On mouse reads at 32×, ABySS took 5.4 h and MEGAHIT 8 h.
  • The aligner matters more than the hardware. A RagTag patch of the species A assembly with the aligner nucmer was stopped after almost a week; the same patch with minimap2 finished in minutes.
